# Architecture (M1 explorer, M2 plans, M3 replace and apply, M4 import, M5 Workspace Hub, M6 guided init, M7 workspace lifecycle, M8 project tools, M9 execution profiles, M10 drift detection, M11 dependency graph, M12 workspace comparison, M13 operation history, M14 apply preflight, M15 Git context, M16 cloud discovery, M17 cost estimates)

## Runtime and trust boundaries

`cmd/hclaro` parses flags, validates one explicit project root, resolves one engine executable, binds `127.0.0.1`, generates 256 random session bits, and serves embedded assets. State loading runs asynchronously so a slow backend does not delay the HTTP UI. Each child has a 45-second deadline and cancellation; Ctrl+C/SIGTERM cancels reads and shuts HTTP down with a bounded grace period.

Launch uses only the read interface: `Version`, `Workspace`, and `State`. A separate `Planner` interface adds `Plan` and `ShowPlan`, and a separate `Applier` interface has one method, `Apply(path)`, which applies a saved plan file and accepts no options. Both are used only by the operation manager after explicit, CSRF-protected requests (see [Plans and operations](#plans-and-operations) and [Saved-plan apply](#saved-plan-apply)). No interface has an import or state-mutation method: imports are import blocks planned through `Plan`, whose only additions are an optional `-generate-config-out` file name and, for [drift scans](#drift-scans), `-refresh-only`. A separate `Grapher` interface has one method, `Graph()`, which runs `graph` with no arguments (see [Dependency graphs](#dependency-graphs)). `internal/engine.CLI` is the shared official-CLI adapter for the common Terraform/OpenTofu dialect. Its explicit engine name selects compatibility policy and version fields. It uses `exec.CommandContext` and argv, never a shell. Selection prefers Terraform, then OpenTofu, unless `--engine` forces one. A mock adapter and a compiled fake CLI keep tests independent of installed engines and credentials.

Without `--hub`, the current directory (or `--path`) is the **launch project**, exactly as before. With `--hub`, or when an implicit current directory is not a project, there is no launch project: the launch store reports `no_launch_project` and the operation manager has no planner. An explicit `--path` that is not a project still fails. See [Workspace Hub](#workspace-hub) for registered projects.

The HTTP layer has no direct reference to an engine or filesystem root. It reads the snapshot store and embedded assets, and it can ask the operation manager to start one plan, approve or apply a reviewed plan, or cancel a running operation. Every GET route is side-effect free; browsing can never invoke a command. Hub inspection and opening a Hub workspace run read-only engine commands, so they are CSRF-protected POSTs. It can also ask the manager to preview an import (no side effects) or to write a reviewed import block and plan it.

## Discovery and compatibility

Discovery never walks parents or writes files. The selected root is resolved through symlinks and must contain a recognized project/state filename. Initialization is inferred from the selected data directory or existing local state. Only the initialized backend **type** is read, through a bounded regular-file JSON read; config, credentials, absolute paths and environment values are never returned. `TF_DATA_DIR` can be relative to the selected root or absolute. The lockfile is reported by presence only. Backend configuration is never parsed. When the project is initialized but has no backend metadata, which is what `init` leaves for the default local backend, the root module's `.tf`/`.tofu`/`.tf.json` files are scanned textually for a `backend` or `cloud` block. No match means the default local backend. Any match, including a commented-out block or an unreadable file, keeps the backend unknown. This cannot route a plan to a remote backend: a configured but uninitialized backend makes the engine refuse to plan.

Workspace selection comes from the CLI, including inherited `TF_WORKSPACE`; an error never substitutes `default`. Remote/cloud backend metadata is labeled `remote-exec`. Unknown backend execution mode stays `unsupported`. Read capability is enabled only after a successful state read/parse. Plan capability is enabled only for `local-cli` execution after the version and workspace reads succeed; it stays enabled when no state is recorded yet. A `planReason` explains why planning is unavailable. Saved-plan apply (`canApplySavedPlan`) is enabled only where planning is and the adapter implements `Applier`; remote execution is refused with an `applyReason`. `supportsImportBlocks` and `supportsGeneratedConfig` come from the engine and version (Terraform 1.5+, OpenTofu 1.6+, which is the whole supported range); `canImport` additionally needs `canPlan`, otherwise `importReason` explains why only the manual recipe is offered.

Stable Terraform 1.5–1.17 and OpenTofu 1.6–1.13 are the intended compatibility range. Terraform 1.5.5 has been exercised against a disposable local project (see [M02 evidence](M02-verification.md#real-engine-run)); other versions and OpenTofu only with synthetic output. Version prereleases and unsupported majors/minors are refused; format major 1 is accepted with unknown fields ignored. The common `show -json` subset is documented by [Terraform](https://developer.hashicorp.com/terraform/cli/commands/show) and [OpenTofu](https://opentofu.org/docs/cli/commands/show/). Real providers/versions need a disposable-workspace certification matrix before release.

Inherited credential, workspace and CLI configuration variables are retained. Injected `TF_CLI_ARGS` for the active command are rejected unless all arguments are `-no-color`, preventing file-output/path overrides. `TF_LOG*` is removed, `TF_LOG=OFF` and `CHECKPOINT_DISABLE=1` are forced, and raw stderr is discarded. Diagnostics explain safe troubleshooting categories rather than returning secret-bearing CLI text. This deliberately trades diagnostic specificity for protection in M1.

## Snapshot parsing and redaction

The parser consumes at most 64 MiB of official `show -json` output. It refuses plan JSON, trailing JSON, duplicate/invalid instances, more than 100,000 resources, and module nesting beyond 128. Module paths and resource addresses are retained **exactly as emitted by the CLI**. Dots inside quoted keys are never split. Deterministic opaque IDs derive from canonical addresses; maps index IDs, resource types and provider sources. Root/child module indexes include their direct instance counts. Managed and data modes remain separate.

Attributes are copied through the redactor before a snapshot is published. Values are shown unless they are likely secrets: anything Terraform/OpenTofu marks sensitive (at any depth), attributes whose names contain secret-like words (`password`, `secret`, `token`, `private_key`, `access_key`, `connection_string`, `user_data`, …), and credential-shaped strings (PEM blocks, JWTs, bearer tokens, AWS access key IDs, URLs with embedded passwords, known vendor token prefixes, and long random-looking strings, including plain hex of 20+ characters). Booleans and numbers are shown unless marked or under a secret-like name; strings over 16 KiB are hidden. Nested objects remain navigable; excessively deep values and suspicious map keys are masked. State outputs and raw JSON are never exposed. Potentially unsafe address/provider metadata rejects the snapshot rather than returning misleading altered addresses.

This matches what `terraform plan` itself prints, plus heuristics for secrets a provider failed to mark. It replaced an allowlist of 25 attribute names, which hid most real provider values (tags, enums, booleans, IDs) and made plan review unable to show what changed. The tradeoff: a secret that is not marked sensitive, sits under an ordinary name and does not look random (for example a short human-chosen password in a `description`) is shown. Hex digests such as etags are hidden because plain-hex API keys look the same. There is no reveal switch. Raw subprocess bytes exist only transiently in memory; no state, raw logs or credentials are written by Hclaro. Operation history (below) persists only redacted metadata. Installed engine/provider plugins remain trusted local executables with their own behavior.

## Plans and operations

A plan runs only after `POST /api/v1/plans` with `acknowledgeBackendAccess: true`, which the UI sends only from its preflight dialog. The operation manager allows one operation at a time and refuses new work during shutdown.

1. **Checking workspace.** `workspace show` must still match the workspace recorded at launch; otherwise the run fails with `workspace_changed`.
2. **Planning.** `os.MkdirTemp` creates a private `0700` directory under the OS temp directory (never the project). The engine runs `plan -input=false -json -out=<dir>/plan.tfplan [-var-file=<name>…]` through `exec.CommandContext`. `-lock=false`, `-refresh=false`, `-target`, `-destroy` and arbitrary flags cannot be requested; `TF_CLI_ARGS`/`TF_CLI_ARGS_plan` may only contain `-no-color`. Variable files are bare names chosen from a server-side list of `*.tfvars`/`*.tfvars.json` files in the project root (auto-loaded files, symlinks and unusual names excluded).
3. **Reading plan.** The artifact is set to `0600`, hashed (SHA-256), read back with `show -json <path>` and parsed. If the plan can be applied (see below), the directory is kept as the single retained artifact; otherwise it is removed at once. It is always removed on failure, cancellation, timeout and shutdown.

A replacement plan is the same command with one `-replace=<address>` per selected instance appended. The request carries opaque resource IDs; the manager resolves them against the current snapshot, accepts only `managed` instances, refuses duplicates and more than 50, and passes each exact address as one argv element (quotes and brackets reach the engine verbatim). `-target` is never used. The stored plan records `kind: "replace"` and the requested addresses, and gets a warning for each requested address the plan does not actually replace.

Cancellation sends an interrupt so the engine can stop providers and release a state lock, then kills it after 15 seconds. On Windows the engine starts in its own process group and receives `CTRL_BREAK`, which Go programs such as Terraform and OpenTofu handle as an interrupt; if Hclaro has no console to send it from, the engine is killed immediately. Plans time out after one hour. Shutdown cancels a running plan and waits up to 20 seconds for cleanup. Planning never writes state; a forcefully stopped engine may leave a lock, which Hclaro never removes.

### Saved-plan apply

A plan is **eligible** when the engine reports it applyable, it is not errored, has no deferred changes and has at least one resource (other than read/no-op) or output change, and the workspace capability allows apply. Only the most recent eligible plan keeps its artifact; a newer one supersedes it. An artifact expires after one hour (timer plus a check on every request).

1. **Status.** `GET /api/v1/plans/{id}` includes `apply: {available, reason, artifactRetained, expiresAt}`, computed per request: artifact still held for this plan, not expired, no operation running, workspace not loading, engine/version/workspace unchanged, and the [context fingerprint](#plan-review-model) recomputed and equal.
2. **Preflight.** `POST /plans/{id}/preflight {verifyIdentity}` evaluates every [preflight check](#apply-preflight) on the server and returns the report. If nothing blocks it also returns an opaque binding (256 bits, ten minutes, never past the plan's expiry) that replaces any earlier binding and unused approval.
3. **Approval.** `POST /plans/{id}/approval {preflightBinding, acknowledged}` repeats the status checks, requires the current binding and exactly the warning check IDs the preflight asked to acknowledge (no blanket value is accepted), and returns a 256-bit token valid for five minutes, the action counts, the requested replacements, the command preview and, for destructive plans (delete, replace, forget or unknown actions), the phrase `apply <workspace>`. A new approval replaces an unused one.
4. **Apply.** `POST /plans/{id}/apply {confirmationToken, confirmation}` consumes the token on any use (a mismatch or replay needs a new approval), compares token and phrase in constant time, repeats the checks, evaluates the whole preflight again (a new blocker refuses with `preflight_blocked`, a warning that was not acknowledged with `preflight_changed`, and the binding is dropped), then starts an `apply` operation. The run confirms `workspace show` still matches and that the file's SHA-256 equals the reviewed digest, then executes `apply -input=false -json <file>`. `-auto-approve` is not passed: a saved plan never prompts. `TF_CLI_ARGS_apply` may only contain `-no-color`.
5. **After.** The artifact is deleted after the attempt whatever the result, so a plan is applied at most once; there is no fallback re-plan. If the engine ran, state is re-read through the normal read path. The operation reports `outcome`: `applied`, `not_applied` (refused before the engine ran, or a stale plan/lock refused by the engine) or `uncertain` (failed or interrupted after starting), plus `stateReloaded`.

On startup Hclaro deletes `hclaro-plan-*` directories in the temp directory that are older than plan expiry plus the apply timeout. They can only be left by a process that was killed; the age limit keeps another running instance's artifact safe, and symlinks are not followed.

The engine's own stale-plan check (state serial/lineage) is the secondary defense for changes Hclaro cannot observe, such as another process writing state; it is classified as `stale_plan`. Cancelling an apply interrupts the engine like a plan; this can leave resources partly changed, which the UI says. Applies time out after two hours.

### Apply preflight

`internal/preflight` turns collected facts into typed checks `{id, title, severity: block|warn|info, status: pass|fail|unknown, evidence, remediation, source}`. Evaluation does no I/O; `operations.Manager.facts` collects the input (it hashes the saved file and runs the Git probe) and the same function runs for the preflight request and again inside `StartApply`. Unknown is never treated as passed: an unknown blocking check blocks, an unknown warning needs an acknowledgement.

| Check | Severity | Fails when |
| --- | --- | --- |
| `context.identity` | block | engine, version or workspace differ from the plan's |
| `context.profile` | block | the execution profile changed or was removed (profile-bound plans only) |
| `context.fingerprint` | block | the [context fingerprint](#plan-review-model) differs |
| `plan.eligible` | block | the plan is errored, deferred, not applyable or has no changes |
| `plan.artifact` | block | the saved file is gone, unreadable (unknown) or its SHA-256 differs from the reviewed digest |
| `plan.ttl` | block | the plan expired |
| `engine.supported` | block | engine or version outside the supported range |
| `backend.execution` | block | remote execution, an unverified backend (unknown) or apply unavailable |
| `operations.conflict` | block | another operation runs, the root is claimed (for example by a Hub init), the workspace is loading, or Hclaro is stopping. Locks held by other tools are left to the engine |
| `policy.valid` | block | `.hclaro/policy.json` is refused |
| `git.worktree` | policy (default warn) | uncommitted or untracked files; unknown when Git is missing or fails; info outside a repository unless the rule blocks |
| `context.production` | policy (default warn) | workspace, profile or AWS profile name matches a production-like pattern |
| `plan.destructive` | info, or policy limit | the plan deletes, replaces, forgets or has unrecognized actions; the typed phrase covers it |
| `plan.scope` | warn | a replace or import plan changes resource instances that were not requested |
| `git.source` | block, or warn | IaC files of the root or its local modules differ from the plan's [source fingerprint](#git-context) (block; unknown blocks too); HEAD moved with identical files (warn). Omitted when no fingerprint was recorded |
| `cloud.aws.identity` | info, or policy | shown for AWS resources, an AWS profile or an account rule; unknown until verified |

The report also carries the context identity (project folder name, engine and version, workspace, backend and execution mode, profile, digest, short fingerprint) and the impact of the **whole** plan: counts per action, destructive count, requested addresses, the number of other changes, the high-risk list (delete, replace, forget, unknown) and every non-no-op change with a `requested` marker, capped at 5,000 rows with a `truncated` flag.

**Policy.** A project may contain `.hclaro/policy.json`:

```json
{
  "version": 1,
  "rules": {
    "gitDirty": "warn",
    "productionLabels": {"severity": "warn", "patterns": ["prod", "*-prod", "production"]},
    "destructiveLimit": {"severity": "block", "max": 10},
    "awsAccounts": {"severity": "block", "allowed": ["123456789012"]}
  }
}
```

Severities are `off`, `info`, `warn` and `block`. Decoding is strict (unknown fields, other versions, oversized files over 64 KiB, symlinked files or a linked `.hclaro` are refused) and a refused file blocks with a generic reason; its content is never echoed. Patterns are case-insensitive globs over letters, digits, `.`, `_`, `-` and `*`. The policy has no code, no URL and no way to relax the built-in blocking checks. It lives in a hidden directory, so it is outside the plan fingerprint, but it is read again at apply.

**Git probe.** `git -c core.fsmonitor=false -c core.untrackedCache=false -C <root> status --porcelain=v1 -z --untracked-files=normal` with `GIT_OPTIONAL_LOCKS=0`, `GIT_TERMINAL_PROMPT=0`, a 10-second timeout and 1 MiB output bound; stderr is discarded. It runs only if `.git` exists in the root or a parent. The whole repository's status counts, not only the project folder. Up to ten paths are shown; credential-shaped or control-character paths are dropped.

**Identity probe.** Only when the request sets `verifyIdentity` (the **Verify AWS identity** button): `aws sts get-caller-identity --output json` with the plan's environment (a profile-bound plan's composed environment, else Hclaro's), `AWS_PAGER=` and `AWS_CLI_AUTO_PROMPT=off`, empty stdin, a 20-second timeout and stderr discarded. Only the 12-digit account and a validated ARN are kept (the user ID is dropped); the result is kept with the binding so a re-check does not call AWS again. It reports the CLI's identity now; providers that assume other roles can still reach another account, which the evidence says. Hclaro never derives an account from a profile name.

**Recording.** The apply operation records `preflight: {checkedAt, policy, acknowledged, identityVerified}` (check IDs only) and one log line with counts. Evidence, Git paths, account IDs and ARNs are returned only in the preflight response and never logged or written to history.

### Git context

`internal/gitctx` reads the Git context of the launch project and of Hub projects. It never changes a repository.

**Runner.** Git runs only through `gitctx.Runner`. The real runner accepts three subcommands with a fixed option set each and refuses everything else before looking up `git`: `rev-parse --path-format=absolute --show-toplevel --git-dir --git-common-dir`, `status --porcelain=v2 --branch -z --untracked-files=all --no-renames --ignore-submodules=all`, and `diff --no-ext-diff --no-textconv --no-color --no-renames --unified=3 HEAD -- :(literal)<path>` (exactly one literal pathspec, taken from Git's own status output, never from a request). Every command is `git -c core.fsmonitor=false -c core.untrackedCache=false --no-pager --no-optional-locks -C <dir> …` with argv (no shell), a 10-second timeout, bounded stdout (64 KiB, 2 MiB for status, 1 MiB for a diff) and stderr discarded. The child environment drops every inherited `GIT_*` variable (so `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_EXTERNAL_DIFF`, `GIT_CONFIG_*` cannot redirect or extend it) and sets `GIT_OPTIONAL_LOCKS=0`, `GIT_TERMINAL_PROMPT=0`, `GIT_NO_REPLACE_OBJECTS=1`, `LC_ALL=C`. External diff drivers and textconv filters are disabled; a `binary` attribute yields a binary notice. Requires Git 2.31 or later (`--path-format`); tested with 2.41. Repository configuration that Git itself applies to read commands (for example `safe.directory` refusals) is respected and reported as unavailable.

**HEAD without Git.** The badge (`GET …/git/head`) and plan fingerprints read `HEAD`, `commondir`, the checked-out ref and `packed-refs` (bounded regular files) of the nearest `.git` entry, following a `gitdir:` file for linked worktrees and submodules. M13's history uses the same reader.

**Scope.** The canonical project root, the repository top level as the base (or the root outside a repository) and the **local modules**: entries of `<data dir>/modules/modules.json` whose source starts with `./` or `../`, resolved with `EvalSymlinks` inside the base and outside the data directory (at most 200). Downloaded modules are excluded. Files are IaC files only (`.tf`, `.tofu`, `.tf.json`, `.tofu.json`, `.tfvars`, `.tfvars.json`, `.terraform.lock.hcl`): the root recursively (hidden directories and `node_modules` skipped, symlinked directories not followed), module directories non-recursively, at most 5,000. A symlinked file counts only when its target is inside the base; every read resolves the path again and requires a regular file inside the root or a local module directory, so a link swapped after listing is refused (`outside_scope`).

**Status.** One `git status` in the top level. Records are parsed strictly (unknown record types, malformed fields, absolute or `..` paths and a missing `branch.oid` refuse the whole output as `git_output_invalid`; nothing partial is shown). Entries are classified by place: `root`, `module` or `outside`. Only IaC files in the root and local modules are listed (at most 500), each with an opaque ID: the first 128 bits of HMAC-SHA256 over the base and the base-relative path, with a random per-process key. Changes elsewhere and non-IaC files are counted. Credential-shaped or control-character paths are counted, never shown. The response carries the repository folder name and the project path inside it, never an absolute path. Warnings: `detached_head`, `unborn_branch`, `untracked_iac`, `outside_changes`, `status_incomplete`.

**Diffs.** A diff request names a file ID; the server runs a fresh status and resolves the ID against it, so stale or forged IDs fail (`file_not_found`). Only `hcl` and `json` kinds are diffed; variable files and the lock file answer `not_diffable`. Untracked files (and every file on a branch without commits) are read directly (512 KiB bound, NUL bytes mean binary) and shown as added. The parser accepts the known extended headers, exactly one file, hunks whose line counts match their headers, and `\ No newline` notes; anything else is `git_output_invalid`. At most 4,000 lines are returned (`truncated`). Every line, and the hunk's section text, goes through `LineRedactor`: literals assigned to names matching `state.RiskyKey` (also unquoted values that are not references such as `var.x`), any literal for which `state.LooksSecret` holds, every line of a heredoc opened under such a name, and lines that are credential-shaped as a whole become `[redacted]`; control and format characters are removed and lines are cut at 400 characters. Diffs are returned only in the response; they are never logged, cached or written to history.

**Source fingerprint.** When a plan starts (before the engine runs, next to the context fingerprint) the manager records `PlanSourceFingerprint {repository, commit, branch, detached, dirty, dirtyKnown, dirtyFiles, contentSha256, files, localModules, recordedAt}`. `contentSha256` hashes the base-relative path and content of every IaC file in scope (256 MiB budget; empty when it cannot be computed). `dirty` comes from one status. For an import plan with engine-generated configuration, the fingerprint is taken again after the plan when the context fingerprint proves no other edit happened. Comparison (`GET /plans/{id}` → `sourceStatus`, and the `git.source` preflight check, which `StartApply` evaluates again) recomputes HEAD and the content hash without running Git: different content is `files_changed` (apply unavailable and blocked), a different commit with the same content is `head_changed` (warning to acknowledge), and an incomputable hash is `unknown` (blocks). The context fingerprint already covers files under the root; the source fingerprint adds local modules outside it.

**Source references.** `GET /resources/{id}/source` (launch) and `GET /contexts/{cid}/resources/{rid}/source` (Hub) take the resource's recorded mode, module, type and name from the redacted snapshot, map the module path to a local module directory through the manifest (the address grammar of `internal/imports`), and scan that directory's `.tf`/`.tofu` files for the `resource` or `data` block header (`block` confidence) or `.tf.json` files for the declaration (`file`, approximate line). Results are labeled best effort; downloaded modules are `unsupported`.

**Editor links.** `POST …/editor/open {fileId, line, editor}` accepts only `vscode` or `cursor`. The ID is resolved against the scope's files now, the target is read again through the scope check and the line must exist. The server builds `<scheme>://file/<path>:<line>` with every byte outside `[A-Za-z0-9-._~/:]` percent-encoded and hands that one argument to the OS URL opener (`open`, `xdg-open`, or `rundll32 url.dll,FileProtocolHandler`). The response names the base-relative path, not the absolute one.

### Cloud discovery

`internal/discovery` (M16) lists existing AWS objects for the launch workspace on request. It is not an engine operation and does not take the project's operation slot: it never touches state or the project folder.

**Adapter.** `discovery.Runner` runs one AWS CLI call; `Exec` is the real one (`aws` from `PATH`, argv only, empty stdin, 60 s timeout, 8 MiB stdout, stderr only classified). `Allowed` is the allowlist; the catalogue (`Types`) holds, per supported type, the list operation, whether it is global (S3), the documented import ID shape and the state attributes that hold the same identifier. The CLI was chosen over the AWS SDK so the binary keeps no third-party Go dependencies and so SSO, `credential_process` and other credential-chain features behave exactly as in the user's terminal; AWS CLI v1 is refused because its pager/version semantics differ. Pagination uses `--max-items`/`--starting-token`, one page of at most 100 objects per call.

**Context pin.** Every verification, scan and prepared import carries a `Pin`: profile ID and context fingerprint (or `inherited`), AWS profile and region names, workspace and engine of the snapshot. Any difference withholds a scan's results and refuses verification reuse, preparation and the import link. The account is checked with STS at verification, at scan start and at preparation.

**Scan.** Tasks are (type, region) pairs, or one task for S3. A per-scan semaphore (1–4) and a session-wide limit of 4 concurrent calls bound load; at most 2 scans run. Throttled calls are retried up to 4 attempts with 0.5 s/1 s/2 s backoff. Credential failures (expired SSO, missing or invalid credentials, unknown profile, identity changed) stop the scan; other failures (access denied, opt-in region, malformed page) fail only their task, and the scan is `partial`. Candidates are de-duplicated by a hash of type, account and identifier; regions that reported the same object are merged. Scans (10) and verifications (20) are kept in memory.

**Matching.** `Match` runs on every read against the current snapshot, so a re-read after an import updates labels. Only managed instances of the same type count. An instance is comparable when one of its identifier attributes has the documented shape or it records an ARN; a candidate is `already_tracked` only for exactly one hit without a contradicting ARN, `possibly_untracked` only when every instance of the type is comparable and none hits, and `unknown` otherwise. `aws_db_instance` accepts the v5 `identifier` and the v4 `id`; a v5 resource ID (`db-…`) is not an import ID.

**Import link.** `Prepare` returns a prefill with a one-time token (15 minutes). `POST /api/v1/imports` with `discoveryToken` is refused unless the token matches the current pin, the request's import ID and the address's resource type; the rest of the M04 flow (preview, new file, reviewed plan) is unchanged.

### Imports

An import is an import block in a new configuration file plus an ordinary plan; Hclaro never runs the `import` command.

1. **Preview.** `POST /api/v1/imports/preview {address, id, provider, file, generateConfig}` is side-effect free (POST only so the ID never appears in a URL). `internal/imports` parses the address into a strict subset of resource instance addresses: optional `module.<name>[key]` steps, then a managed `type.name[key]`; string keys may not contain quotes, backslashes, `]` or template sequences, so the address is written verbatim. The ID must be 1–2048 characters without control characters or surrounding spaces; credential-shaped IDs (`state.Suspicious`) are refused because they would be written to configuration in plain text. It is rendered as an HCL string with `\`, `"` escaped and `${`/`%{` doubled. The destination must be a new bare `*.tf` name in the root that is not an override file. Checks against the current snapshot and configuration:
   - **State.** The address must not be in state; another managed instance of the same type whose recorded `id` equals the import ID is a collision (the comparison uses the redacted snapshot, so an `id` hidden as secret-like cannot be matched). If the snapshot is unreadable, the import is blocked, except when no state has been recorded at all.
   - **Configuration.** The resource block is found by a textual scan of the declaring module's `.tf`/`.tofu` files (and `resource` objects in `.tf.json`). Child modules are located through `.terraform/modules/modules.json`; module directories outside the project and data directory are not read. A missing block blocks the import unless configuration generation is requested and possible; an unreadable or unknown module is a warning. Top-level `count`/`for_each` in the block (strings, comments and heredocs skipped) is compared with the instance key; mismatches are warnings because the scan is not an HCL parser.
   - **Generation.** Allowed only for root-module, unindexed addresses with no existing block and a capable engine. The engine writes `<file stem>_generated.tf`, which must not exist.
   - **Duplicates.** A `to = <address>` line in a root file (import or moved block) blocks a second import block.
   The response includes the exact file content, a SHA-256 over the destination names and content, and a manual recipe (block, `plan -out`, `show`, `apply` of the saved file; the legacy `import` command labeled as writing state without a plan, with POSIX shell quoting).
2. **Start.** `POST /api/v1/imports` repeats the request with `previewSha256`, `acknowledgeWrite: true` and `acknowledgeBackendAccess: true`. Under the operation lock the manager re-runs every check, requires the digest to match, and writes the file: a `0644` temporary file in the root (`.hclaro-import-*.tmp`) is written and synced, then hard-linked to the final name, which fails if anything (including a dangling symlink) exists there; the project directory must still resolve to the launch root. Where hard links are unavailable it falls back to an exclusive create. Then the plan starts as in [Plans and operations](#plans-and-operations), with `-generate-config-out=<name>` when requested.
3. **Review.** The stored plan has `kind: "import"`, the target, and `imports` (changes with `importing`, whatever their action). A warning is added if the plan does not import the target. A generated file is read back (regular file, at most 1 MiB) and returned only as a display copy with values under secret-like names, credential-shaped or random-looking values, known input values and heredoc bodies replaced. The [context fingerprint](#plan-review-model) is taken before the plan with the generated file excluded; after the plan it is retaken the same way and, only if unchanged, replaced by the full fingerprint including the new file. Any other edit made while planning therefore makes the plan unapplicable, and any later edit to either file does too.
4. **Apply.** As for any plan. An import-only plan is a `no-op` action, so imports count as changes for eligibility. Because an import writes state, the typed phrase is required whenever `imports > 0`. After an apply, state is re-read and the imported instance appears in the explorer.

Hclaro never deletes the files it wrote: they are the user's configuration once approved. Recovery after a failed plan or apply is described in the UI (retry with any plan, or delete the files to back out). Apart from configuration the engine generates on request, the import file and its short-lived temporary file are the only writes Hclaro makes in the project root.

### Cost estimates

`internal/cost` (M17) estimates the recurring monthly cost change of a reviewed plan through an optional provider. It is not an engine operation, does not take the operation slot and never blocks a plan, preflight or apply: estimates have their own one-at-a-time slot in `cost.Service`.

**Provider abstraction.** `cost.Runner` (`Find`, `Run`) is the adapter boundary; `cost.Exec` is the Infracost CLI, `costtest.Runner` the recording fake. The service exposes the task's operations: `CanEstimate` (strict mode, opt-in, installed, supported version), `Disclosure` (an `ExternalDataDisclosure`), `Start` (`Estimate`) and `Cancel`. Infracost was chosen because it is the established open-source CLI that prices Terraform plan JSON; it always needs a pricing API (Infracost's hosted Cloud Pricing API or a self-hosted one), so `offlineAvailable` is false and `--strict-local` disables the feature rather than pretending a remote API is local.

**Opt-in.** `Capabilities` never starts a process (only `exec.LookPath`). `POST /cost/opt-in {acknowledged:true, disclosureVersion}` must name the current disclosure version; it then runs `infracost --version` and accepts only v0.10.x. The opt-in is in memory for the session; `opt-out` ends it and cancels a running estimate.

**Cost input.** While the plan's `show -json` document is in memory, `operations` derives `cost.Minimize(document)` and keeps it with the plan (memory only, 8 MiB cap). It keeps the document shape Infracost parses (`planned_values`, `prior_state.values`, `resource_changes` with actions and filtered before/after, `configuration.provider_config` names with a literal region, configuration references) and drops everything listed in [SECURITY](../SECURITY.md). Each value goes through the redaction rules (sensitive markers at any depth, risky names, `LooksSecret`) plus a list of free-text attribute names, strings over 1 KiB and control characters. A dropped list element becomes `null` so indexes keep their meaning.

**Run.** `Start` binds the estimate to `{planId, artifactSha256, fingerprint, engine, workspace, profileId}` and refuses when the plan's context already changed (`ContextStatus`). The run checks the version again, creates a `0700` `hclaro-cost-*` directory, writes `plan.json` (`0600`, `O_EXCL`), runs `breakdown --path <file> --format json --no-color --log-level=warn` (3-minute timeout, 16 MiB stdout, stderr only classified into `auth_required`, `pricing_unavailable` or `failed`) and removes the directory on every path. Environment: allowlist plus `INFRACOST_SKIP_UPDATE_CHECK=true`, `INFRACOST_ENABLE_CLOUD=false`, `INFRACOST_ENABLE_DASHBOARD=false`, `INFRACOST_SELF_HOSTED_TELEMETRY=false`, `INFRACOST_NO_COLOR=true`, `INFRACOST_LOG_LEVEL=warn`. These settings follow Infracost's documented environment variables; they were exercised only against the synthetic CLI.

**Aggregation.** `Aggregate` decodes Infracost JSON schema 0.x (`projects[].pastBreakdown|breakdown.resources[]` with `costComponents` and `subresources`, `summary.unsupportedResourceCounts|noPriceResourceCounts`) into fixed structs. Amounts must be plain decimals and are summed with `math/big.Rat`, rounded half away from zero to cents only for output. Only managed, non-no-op, non-deposed changes of the reviewed plan become line items; a provider resource whose name is not a plan address is dropped (`unattributed`). Status per item: `estimated`, `partial` (some components unpriced), `usage_unknown` (nothing priced), `unsupported`/`free` (by the summary's type counts), `not_estimated` (forget, unknown action, or a change priced on one side only). Unpriced items carry no amounts and are excluded from totals. `coverage.percent` = (estimated + partial) / (changed − free), floored, `null` when nothing is cost-bearing. Totals: `monthlyDelta` (sum of item deltas), `addedMonthly` (creates), `removedMonthly` (deletes), `changedDelta` (updates/replaces), `pastMonthly`/`projectedMonthly` (all priced plan addresses, including unchanged ones).

**Staleness.** Every read of an estimate recomputes `stale`: the plan is gone, its digest/fingerprint/workspace/engine differ, or `ContextStatus` reports a change. A new plan never inherits an estimate.

**Persistence.** Completed estimates add an `AggregateRecord` (no addresses, line items or paths; the project is a salted SHA-256 key of the root plus its folder name) to `cost-estimates.json` (version 1, last 50, strict decoding, `0600`, atomic rename). An unreadable file is treated as empty and replaced on the next write.

### Progress logs

The engine's machine-readable UI stream (`-json`) is translated, not forwarded. Hclaro renders only typed events: refresh start/complete (address only, no IDs), planned change (address, action, reason), drift, apply start/complete/errored (address and action, no IDs), change summary, output count, diagnostics and generic log messages. Apply progress ticks and provisioner output are dropped; provisioner output can echo secrets. Addresses that look like secrets are replaced. Free text (diagnostic summaries/details and log messages) is cleaned in two steps. First, known input values are replaced with `[redacted]`: `TF_VAR_*` environment values and string values (quoted literals, heredoc lines, JSON strings) from the selected variable files and the files the engine loads automatically (`terraform.tfvars`, `*.auto.tfvars`, with `.json` variants). Values shorter than four characters are skipped. Collection over-matches, so map keys and non-secret inputs such as a region name are redacted too. The values are held only while the plan runs. Then a line sanitizer withholds credential-shaped lines and assignments to risky attribute names, strips control characters, and truncates. The line checks are still heuristic: a secret that is neither a known input nor recognizable, such as one returned by a provider API, can still be shown. Non-JSON stdout is withheld. stderr is never returned; it is only keyword-classified (`state_locked`, `credentials`, `init_required`, `network`).

Each operation keeps a ring buffer of at most 10,000 events or 2 MiB, whichever is reached first; dropped events are counted and reported. Logs for the 10 most recent operations and metadata for 100 are kept in memory only. Persistent [operation history](#operation-history) keeps at most the last 40 sanitized lines of each operation.

### Plan review model

`internal/plan` accepts only `show -json` plan documents (format major 1 with `planned_values`; state documents are refused) up to 64 MiB and 100,000 changes. Actions are classified from the ordered list: `create`, `update`, `delete`, `read`, `no-op`, `forget`, and `replace` for both `delete,create` (destroy before create) and `create,delete` (create before destroy). Any other combination is `unknown`, counted, and flagged as potentially destructive. CLI order is preserved. Every resource change is kept, including no-ops, data reads, deposed objects, moves (`previous_address`) and imports. Drift (`resource_drift`) is kept separately. Output changes are kept; their values go through the same policy, with the output name as the key. `deferred_changes` produce a warning. Errored plans are flagged.

Attribute diffs are computed on **raw** values, then redacted, so a change to a sensitive value is still listed as a change. Each row has a path (`tags["Name"]`, `ingress[0].cidr_blocks`), before/after values through the state redaction policy (applying the nested sensitivity marker at that path, so a row whose value is an object still hides its marked children), and markers for `unknown` (`[known after apply]`), `sensitive` (from `before_sensitive`/`after_sensitive`), and `forcesReplacement` (from `replace_paths`). Rows are capped at 1,000 per change. Secret-shaped addresses, output names or deposed keys reject the plan rather than display altered identifiers.

A stored plan records the engine, workspace, variable files, requested replacements, artifact SHA-256 and a context fingerprint taken **before** the engine runs, so edits made while planning count as a change. The fingerprint is a SHA-256 over:

- engine, version, workspace and selected variable files;
- configuration, variable and lock files under the root (hidden directories skipped);
- from the data directory (`.terraform` or `TF_DATA_DIR`): backend metadata, the selected workspace file, the module manifest and installed module sources;
- the planning environment: `TF_VAR_*`, `TF_WORKSPACE`, `TF_DATA_DIR`, `TF_CLI_ARGS`, `TF_CLI_ARGS_plan` and `TF_CLI_CONFIG_FILE`;
- for a profile-bound plan, the composed child environment instead of Hclaro's and the profile's [context fingerprint](#execution-profiles) as a label.

The plan detail response recomputes it and reports `contextChanged`; approval and apply refuse any mismatch. Hclaro's environment is fixed for its lifetime, so the environment part matters only once fingerprints are compared across launches. Provider plugin binaries are covered only through the lock file's checksums. The fingerprint does not detect provider-side or state changes; the engine's stale-plan check covers state.

### Drift scans

A drift scan is an explicit `POST /api/v1/drift-scans` with `acknowledgeProviderAccess: true`, which the UI sends only from its preflight dialog. It runs in the launch operation manager's single slot (and the shared root claim), like a plan, and is refused with `drift_unsupported` and a reason when `DriftCapability` fails: no planner, remote execution (a remotely run refresh-only plan cannot be verified), planning unavailable, an engine outside `engine.RefreshOnlySupport` (Terraform 1.5+, OpenTofu 1.6+: the whole supported range), or no recorded state.

1. **Checking workspace**, as for a plan (`workspace_changed` otherwise).
2. **Scanning.** A private `0700` `hclaro-drift-*` directory is created and the context fingerprint is taken. The engine runs `plan -input=false -json -out=<dir>/drift.tfplan -refresh-only [-var-file=…] [-parallelism=…] [-lock-timeout=…]`. `PlanRequest.RefreshOnly` refuses `-replace` and `-generate-config-out`. The UI stream is translated like a plan's (`drift` kind: the change summary is replaced by "Refresh-only plan complete").
3. **Reading scan result.** `show -json` on the file, then `drift.Analyze`, which runs `plan.Parse` and refuses (`not_refresh_only`) any document with a non-no-op `resource_changes` entry: Terraform and OpenTofu never propose changes in refresh-only mode, so such a document is not a scan. Each managed `resource_drift` record is classified: `delete` → **missing**, `update` → **changed** (or **cannot verify** when every differing attribute is unknown), `no-op` with unknown values → **cannot verify**, anything else → **unrecognized** (never safe). Data sources are counted and skipped. Attribute rows become `{path, recorded, observed, kind, sensitive}`; an unknown observed value is `cannot_verify` with no value, and the full observed tree uses `[cannot verify]` instead of the plan marker `[known after apply]`.
4. The directory is removed on every path. Nothing is retained, listed under plans or passed to `Applier`.

Outcome: `completed` (exit 0, not errored or incomplete, no error diagnostics, no unrecognized record) with `drift_detected`, `cannot_verify` or `no_drift`, and `exhaustive: true`; `partial` when the engine failed but saved a readable plan, or the document is errored/incomplete — records are kept, no outcome; `failed` (`state_locked`, `credentials`, `network`, `init_required`, `plan_failed`, `plan_read`, `plan_format`, `not_refresh_only`, `unsafe_cli_args`, `workspace_*`, `timeout`) and `cancelled` (`cancelled`, `shutdown`) with no records. Engine diagnostics are the sanitized ones from the log.

Scans are `DriftScan` records in memory: at most ten, dropped after 12 hours, holding only redacted values, the context and the fingerprint (not serialized). Every read recomputes freshness: the snapshot must not be loading and must have the scan's workspace, engine and version, and the fingerprint (recomputed with the scan's variable files and, for a profile, the re-resolved profile) must be equal. Otherwise `current: false`, a `staleReason`, `withheld: true` and an empty resource list; details return 409 `scan_stale`. Resource IDs for the inspector are recomputed for current scans only (`sha256(address)` present in the snapshot as a managed resource; none for deposed objects). `SweepStale` also removes old `hclaro-drift-*` directories.

### Dependency graphs

A graph is an explicit `POST /api/v1/graphs` with `acknowledgeEngineRun: true`, sent only from the UI's preflight dialog. It uses the launch operation manager's single slot and root claim, binds an execution profile like a plan, and is refused with `graph_unsupported` and a reason when `GraphCapability` fails: no planner, remote execution (not verified), planning unavailable (graph needs the same initialized working directory), or an engine outside `engine.GraphSupport` (the whole supported range). Empty state is allowed: the graph describes configuration.

1. **Checking workspace**, as for a plan.
2. **Generating graph.** The context fingerprint is taken, then `engine.Grapher.Graph` runs exactly `graph` (`engine.GraphArgs`). No `-plan`, `-type` or `-draw-cycles` is ever passed, so no saved plan or path reaches the engine; `TF_CLI_ARGS_graph` with anything but `-no-color` is refused like other commands. Stdout is capped at 16 MiB (`graph_too_large`), stderr is only classified (`init_required`, `credentials`, `network`, `state_locked`, otherwise `graph_failed`), and the command has a 3-minute limit with interrupt-then-kill cancellation.
3. **Reading graph.** `graph.Parse` reads the DOT subset the engines write (`strict`/`digraph`, quoted IDs with `\"` and `\\` escapes and `+` concatenation, comments, attribute statements, ports, nested subgraphs and clusters, chained edges and edges to subgraphs), bounded to 20,000 nodes, 200,000 edges and 64 nesting levels. Anything else is `graph_format`; an undirected graph is refused. Node IDs are normalized: `[root] ` is removed; `(expand)` and `(prepare state)` merge into their node; `(close)`, `destroy`/`deposed`, `cleanup`, `meta.*` and `root` nodes are dropped, because they depend on everything and would make every node reachable; any other suffix keeps the node as **unknown**. Names are classified by address grammar into resource, data, module, provider, variable, local, output, check, ephemeral or unknown, with the module path. A name that `state.Suspicious` flags is replaced by `[redacted node]`. Only labels in the ID are used; DOT labels and attributes are discarded. Self-loops and duplicate edges are dropped. Cycles are strongly connected components (iterative Tarjan). For each resource or data node, `ResourceEdges` links it to the nearest resources reached through internal nodes only; such a link is `derived` unless the engine declared it directly (bounded to 4 million steps, then `derivedTruncated`).

Format: `resources` when no ID has the `[root] ` prefix (Terraform 1.7+), otherwise `full` (earlier Terraform, OpenTofu). Graphs are `GraphRun` records in memory, at most five, for 12 hours, holding the parsed model, the context and the fingerprint (not serialized). Freshness is checked on every read like a drift scan; a stale graph returns `withheld: true` and no nodes or edges, and impact requests return 409 `graph_stale`.

Reading a graph annotates nodes against the current snapshot. A resource node with configuration address `A` maps to every recorded instance of the same mode whose address, with all instance keys removed (`graph.ConfigAddress`, quote-aware), equals `A`; an instanced node maps only to its exact address. Mapped nodes are `exact` (with up to 25 explorer IDs and a count), unmapped ones `configuration`; internal nodes are `internal`, unparseable ones `unknown`.

`GET …/nodes/{node}` runs `Analyze`: direct dependencies and dependents, and breadth-first upstream (what it depends on) and downstream (what depends on it: the potential impact) sets with distances, visiting each node once so cycles terminate; lists are capped at 2,000 with totals. With `planId`, the plan must be stored, for the same workspace and engine, not errored, incomplete or deferred, and its context unchanged (`ContextStatus`), otherwise 409 `plan_not_current`. Its non-no-op changes are mapped to nodes (exact instanced node, then configuration address, same mode) and split into `inImpact` (at the node or a node that depends on it), `elsewhere` and `unmapped`. The graph never asserts that a dependency causes a change.

Not implemented: `graph -plan=<saved plan>` (the engine's apply-walk graph). Its node names are walk-internal and version-specific, and passing a saved plan path would couple the read-only graph to the apply artifact; the plan view is instead the configuration graph with the reviewed plan's confirmed changes overlaid.

## Workspace Hub

### Vocabulary

A **project** is one canonical root folder, an optional engine preference and display metadata. A **CLI workspace** is a state namespace inside a project. The **CLI-default** workspace is the one recorded in the project's data directory (`environment`), which `workspace list` marks. A **UI-selected** workspace exists only in a browser tab's URL and in the read context it opens. A profile, account, backend or `terraform.workspace` value is none of these, and nothing is inferred from names except a visible "production-like name" hint (`prod`, `production`, `prd`, `live` as words), which never implies criticality.

### Registry

`projects.json` lives in `os.UserConfigDir()/hclaro` (or `HCLARO_CONFIG_DIR`, absolute only). It is `{"version":1,"projects":[{id, alias, root_path, engine_preference, pinned, added_at, last_opened_at, last_workspace}]}`; array order is the user's order. IDs are 128 random bits. Nothing else is stored: no environment values, credentials, backend configuration, engine paths or state.

Writes go to a `0600` temporary file in the same directory, are synced and renamed over the old file. Every change re-reads the file first, so another Hclaro process's edits survive unless both write at the same instant (last writer wins; the file is never torn). On startup, a file that cannot be decoded (invalid JSON, unknown fields, invalid entries, over 1 MiB) is renamed to `projects.json.corrupt-<UTC time>` and the registry starts empty, with a notice. A file from a newer schema, an unreadable file, or a file that becomes undecodable during the session is never overwritten: the registry is read-only until restart. Up to 200 projects.

Adding a project requires an absolute path (no `~`), cleaned and resolved with `EvalSymlinks`, that is a readable directory with a recognized file (`workspace.Root`). Duplicates are refused by canonical path and by `os.SameFile`, so a symlink or case variant of a registered folder is rejected with the existing ID. Aliases are 1–80 characters with no control or format characters (bidi overrides included) and no surrounding spaces; the default is the folder name. Repairing a path validates the new one the same way. Removing an entry deletes only the entry.

The folder chooser (`POST /projects/browse`) lists the subdirectory names of one folder, default the home directory: hidden names and `node_modules` skipped, no files, at most 500 entries, and only the listed folder itself is checked for project files. It never recurses.

### Status and inspection

`GET /projects` runs no command. Each card's status comes from the file system: `missing`, `unreadable`, `path_changed` (the stored canonical path now resolves elsewhere, for example a parent replaced by a symlink), `not_project` or `ready`; ready projects add `workspace.Inspect` (initialized, backend type, lockfile).

`POST /projects/{id}/inspect`, which the UI sends when a project page opens, resolves the engine (preference, else Terraform then OpenTofu) and runs `version -json` and, for initialized projects, `workspace list`. Both drop any inherited `TF_WORKSPACE`; for `workspace list` this makes the marked entry the persisted CLI default. The list parser accepts the shared text format (`* ` marks the selected one), returns at most 1,000 names matching `^[A-Za-z0-9_-]{1,90}$` that do not look like credentials, and counts the rest as hidden. The result is cached in memory for the session.

### Read contexts

`POST /contexts {projectId, workspace}` returns an immutable context: project ID, canonical root, engine name and executable, workspace and `TF_DATA_DIR`, plus its own `workspace.Store`. The same tuple returns the same context (`reused: true`) unless `reload: true`, which closes it and starts a fresh read. At most eight contexts are kept; the oldest is closed first. Reads run in the background, three at a time, under a context cancelled on shutdown.

A context's engine is an `engine.CLI` with `SelectedWorkspace` set: each child's environment drops the inherited `TF_WORKSPACE` and gets `TF_WORKSPACE=<workspace>`. Hclaro's process environment is never modified, and opening or switching a context never runs `workspace select`, `new` or `delete`; only the reviewed workspace commands below do. The store is created with `workspace.NewScoped`; its read is:

1. `version -json`; then the usual initialization check.
2. `workspace list` (no `TF_WORKSPACE`): the workspace must exist, otherwise `workspace_missing` and nothing else runs.
3. `workspace show` must print the selected workspace. This proves the engine honored `TF_WORKSPACE`; otherwise `workspace_mismatch` and no state is read.
4. `show -json`, parsed and redacted exactly like the launch project.
5. Before publishing, the read must not have been cancelled and the root must still be the same directory (`os.SameFile` and `EvalSymlinks`); otherwise `path_changed` and the snapshot is discarded.

The engine is wrapped so only `Version`, `Workspace` and `State` are reachable; scoped capabilities are always `canPlan`, `canApplySavedPlan` and `canImport` false with one reason. Plans, applies and imports stay bound to the launch store and its CLI-selected workspace.

An absolute `TF_DATA_DIR` applies to every project at once, so a shared data directory could pair one project's configuration with another's backend initialization: inspection reports `shared_data_dir` and contexts are refused. A relative value resolves inside each root and is shown read-only. `TF_CLI_ARGS*` keeps the M1 rule (only `-no-color`).

Unregistering a project, repairing its path or changing its engine closes its contexts at once and cancels reads in progress; their IDs answer `404 context_closed` with the reason (`project_removed`, `project_changed`, `reloaded`, `evicted`, `initialized`, `workspace_deleted`). A context ID only ever reads its own store, so a resource ID from one context is never found through another. Context responses carry no executable path or environment values.

### Initialization

`GET /projects/{id}/init-status` is the read-only preflight. It resolves the engine with `exec.LookPath` (no execution), inspects the folder (`workspace.Inspect`, plus a textual check for a declared `backend`/`cloud` block) and returns the canonical root, engine, the session's inspected version and CLI default if any, data directory, lock file presence, the display command, notices about inherited settings (names only), the latest init operation, and either `canInit` with a `contextId` or a reason (`missing`/`path_changed`/… project status, `shared_data_dir`, `missing_cli`, `unsafe_cli_args`, `busy`, `too_large`).

The context ID is SHA-256 over: project ID, canonical root, engine preference, resolved engine name and executable path, the executable's size/mode/mtime, `workspace.Fingerprint` of the root (configuration, variable and lock files plus the data directory's backend metadata, `environment` and module manifest) and every `TF_*` variable except `TF_VAR_*` and `TF_LOG*`. Values are hashed, never returned.

`POST /projects/{id}/operations/init {mode:"standard", expectedContextId}`:

1. Recomputes the preflight; refuses with its reason, `project_busy` or `context_changed`.
2. Claims the root in the shared `rootlock.Set` (`project_busy` if held), snapshots `os.Environ()`, resolves an `engine.CLI` with `Environ` pinned and `IgnoreInheritedWorkspace`, stats the root and executable and recomputes the context ID with the pinned values.
3. Starts an `operations.Inits` operation (status `queued`) and returns 202. In the background: `version -json` (unsupported or injected flags fail here), choose JSON output (`engine.InitJSON`: Terraform ≥ 1.9 only; OpenTofu's `init -json` has not been verified, so it gets human output), then `Revalidate` (root still resolves to itself and `os.SameFile`, executable `os.SameFile`, context ID unchanged) and only then `init`.
4. The engine runs in its own process group (`Setpgid` on Unix, `CREATE_NEW_PROCESS_GROUP` on Windows). Cancellation sends an interrupt to the group and kills the group after the 15-second grace period. A 30-minute limit applies.
5. JSON mode renders `version`, `init_output`, `log` and `diagnostic` events through the plan translator; other stdout lines are withheld with one notice. Human mode and stderr go through `humanLine`: control and ANSI sequences and diagnostic box borders stripped, `Error:`/`Warning:` split off and recorded as diagnostics, the rest `sanitize`d. The scrub list is the plan's known inputs plus values of credential-shaped environment variables. Raw output is never stored; classification uses the sanitized diagnostics and lines, then a keyword hint from the engine's bounded output tail (`engine.ClassifyInit`).
6. Outcome: `succeeded` only for exit 0 and an existing data directory; exit 0 without one is `unknown` (`unverified`); cancel, shutdown and timeout are `cancelled`/`failed` with their own codes; otherwise `failed` with `backend_migration`, `input_required`, `state_locked`, `lockfile_upgrade`, `version_mismatch`, `registry`, `credentials`, `network`, `backend_config` or `init_failed`. Whether `.terraform.lock.hcl` changed is reported once the engine has run. `Finished` drops the project's inspection and closes its contexts (`initialized`), then the claim is released.

While the root is claimed, `inspect` and `contexts` for that project answer `409 project_busy`, and the launch manager's plan, import and apply refuse to start in that root (and vice versa). Init, workspace and tool operations share `/operations/{id}`, `/events` and `/cancel` with launch operations; the last 50 finished ones are kept (running ones are never evicted), with logs for the last 10. Statuses add `queued`, `cancelling` and `unknown`. The browser disconnecting never changes an operation. Removing or repairing a project while its init runs does not stop it; the operation stays pinned to the root it validated.

**Launch project.** When the initialized root is the folder Hclaro was launched with, the root claim's release also calls `Hub.LaunchChanged`, which runs `Manager.Reread`: the launch store's metadata is replaced by a fresh `workspace.Inspect` and state is read again as at startup (`version`, `workspace show`, `show -json`). The reread happens after the claim is released, only for an init that started, and is skipped if a launch operation or another claim is active. The same reread is available as `POST /api/v1/workspace/reload` (**Read again**).

### Workspace lifecycle

Three commands change workspaces, each only after a review and an explicit confirmation: `workspace new NAME` (the engines also select the new workspace, so it changes the CLI default), `workspace select NAME` (changes the CLI default) and `workspace delete NAME` (never `-force`). Switching the workspace a tab reads is not one of them: it opens another read context with a child `TF_WORKSPACE` and never touches the data directory's `environment` file.

**Engine.** `engine.WorkspaceManager` is a separate interface (`Version`, `ListWorkspaces`, `WorkspaceState`, `ChangeWorkspace`), so read-only, plan and init adapters cannot change workspaces. `WorkspaceArgs` builds the complete argv `workspace <new|select|delete> <name>`; the name must match `^[A-Za-z0-9][A-Za-z0-9_-]{0,89}$` and must not look like a credential, so it can never be read as a flag (`-force`, `-or-create`, `-lock=false`, `-state=…`). Names that `workspace list` returns starting with `-` can be opened read-only but not selected or deleted. `ChangeWorkspace` drops `TF_WORKSPACE` (the engines refuse `new`/`select` while it overrides the selection, and the command must act on the data directory itself) and `TF_LOG*`, refuses `TF_CLI_ARGS`/`TF_CLI_ARGS_workspace` with anything but `-no-color`, runs in its own process group with the init streaming code and a 5-minute limit. `WorkspaceState` is `show -json` with a child `TF_WORKSPACE=<name>`.

**Support.** Whether a project allows these commands comes from file-system metadata only (`Summary.workspaceActions`): it must be initialized; `remote`/`cloud` (remote execution) and unknown backends are refused; other backends must be ones the engines document as supporting multiple workspaces (`local`, `s3`, `gcs`, `azurerm`, `consul`, `cos`, `kubernetes`, `oss`, `pg`). Deletion is enabled only for the `local` backend in this release.

**Review.** `POST /projects/{id}/workspaces/review {action, name}` runs `version -json`, `workspace list` (no `TF_WORKSPACE`) and, for delete, `show -json` for that workspace. It refuses, with a reason and no context ID, when: the project is unavailable or busy; `TF_DATA_DIR` is absolute; the backend is unsupported; the name is unsafe; inherited `TF_CLI_ARGS`, `TF_CLI_ARGS_workspace` or `TF_CLI_ARGS_show` add flags; the engine is missing or unsupported; workspaces cannot be listed (fail closed); `new` names an existing workspace; `select`/`delete` name a missing one; `select` names the current default; `delete` names `default`, the CLI default, the inherited `TF_WORKSPACE` value, or a workspace whose state has any resource instance (managed or data) or output, cannot be read or cannot be parsed; or the CLI default is unknown. The fresh listing also replaces the project's cached inspection. A runnable review returns a context ID: SHA-256 over a static part (project ID, canonical root, engine preference, resolved engine and executable path and identity, configuration and data-directory fingerprint, backend type and mode, action, name, `TF_*` environment) and the listing (names, CLI default, hidden count). The server keeps the review (static hash, listing, notices) for 10 minutes, at most 32, and it is single use.

**Start.** `POST /projects/{id}/operations/workspace {action, name, expectedContextId}` must name a kept, unexpired review for the same project, action and name, else `409 context_changed`. It claims the root in the shared `rootlock.Set` (holder `workspace`; `409 project_busy` while init, a plan or another workspace command holds it), consumes the review, pins `os.Environ()`, and recomputes the static hash. In the background, `operations.Inits.StartWorkspace`: `version -json`; `Revalidate` (root and executable `os.SameFile`, root resolves to itself, static hash unchanged); `workspace list` again, which must equal the reviewed listing exactly (`workspaces_changed` otherwise, for example after `workspace select` in a terminal); for delete, the emptiness read again; then the command. Output is sanitized line by line like human-mode init. Afterwards `workspace list` runs once more (fresh 30-second context, also after a cancel) to record the CLI default before and after.

**Outcome.** `succeeded` only for exit 0 and a listing that shows the effect (`new`: name present; `select`: it is the CLI default; `delete`: name absent). Exit 0 with a failed listing is `unknown`/`unverified`, exit 0 with an unexpected listing `unknown`/`unexpected`: the cached inspection is dropped, nothing is retried and the user is told to list again before repeating. Cancel before the command started is `cancelled_before` (nothing changed); during it, `cancelled` with "may or may not have taken effect". Failures are classified (`workspace_exists`, `workspace_missing`, `workspace_active`, `workspace_default`, `workspace_not_empty`, `workspaces_unsupported`, `workspace_overridden`, `invalid_name`, `state_locked`, `credentials`, `network`, `workspace_failed`). Nothing undoes a changed CLI default automatically. Open read contexts stay valid (they never depended on the CLI default) except those of a deleted workspace, which close with `workspace_deleted`.

Changing the CLI default of the project Hclaro was launched with makes the launch project's plans and applies refuse (`workspace_changed`) until it is read again (**Read again**) or Hclaro restarts, because they verify `workspace show` against their snapshot; the review says so.

### Project tools

Four read-only utilities run in an open read context: `validate`, `fmt-check`, `providers` and `outputs-metadata`. None writes configuration, state or the data directory, and none is offered as a generic command runner.

**Engine.** `engine.Tools` is a separate interface (`Version`, `Validate`, `FormatCheck`, `Providers`, `OutputsMetadata`), so the read-only state adapter stays minimal and no tool can become init, plan, apply or plain `fmt`. `ToolArgs` returns the complete argv: `validate -json` or `validate -no-color`, `fmt -check -no-color [-recursive]`, `providers`, `output -json`. `capture` runs one command with the shared process-group streaming (`streamLines`, 5-minute limit), keeps at most 8 MiB of stdout and 256 KiB of stderr in memory and reports truncation; a non-zero exit is data, not an error, because validate and `fmt -check` report findings through it. `providers` and `output` are workspace-dependent and get `TF_WORKSPACE=<context workspace>`; `validate` and `fmt` get none (`ErrToolWorkspace` refuses a dependent tool without a workspace). `commandEnv` drops inherited `TF_WORKSPACE`/`TF_LOG*` and refuses `TF_CLI_ARGS`/`TF_CLI_ARGS_<command>` with anything but `-no-color`. `OutputsMetadata` decodes `output -json` into a struct with only `sensitive` and `type`, so values are skipped by the decoder; it returns names (pattern-checked, secret-looking ones counted as hidden), compact type labels (object attribute and tuple element names are counted, not shown) and flags. Its stdout never leaves the function; stderr only yields a category (`ClassifyTool`).

**Start.** `POST /projects/{id}/operations/<tool> {contextId, recursive?}` (`recursive` only for `fmt-check`; unknown fields refused). `Hub.StartTool` requires the context to be open and to belong to the project and its current root; checks project status, absolute `TF_DATA_DIR` and unsafe `TF_CLI_ARGS*` before anything runs; resolves the engine with a pinned `os.Environ()` and the context's workspace and requires the same engine name and executable path the context was opened with (`409 context_changed` otherwise). For `fmt-check` it first enumerates the files the engine reads (`FormatScope`: `.tf`, `.tfvars`, `.tftest.hcl`, plus `.tofu` and `.tofutest.hcl` for OpenTofu, skipping names the engines ignore: hidden, `~` backups, `#…#`; bounded to 5,000 files, 1,000 folders, depth 32). A linked folder refuses a recursive check (`symlinked_directory`) and is listed as skipped otherwise; a linked configuration file resolving outside the root refuses (`symlink_outside_root`). The root is then claimed **shared** (`rootlock.AcquireShared`): tools run alongside each other, while `Acquire` (init, workspace commands, plans) refuses while any shared claim is held and vice versa (`409 project_busy`). `Inits.StartTool` refuses the same tool twice in one context while it runs (`409 tool_running`) and more than 8 running tools (`409 tools_busy`), under the same lock that records the operation.

**Run.** Notices (inherited `TF_WORKSPACE` replaced or not passed) → `version -json` → `Revalidate` (root and executable `os.SameFile`, root resolves to itself) → the command. Every printed line passes through `humanLine` (scrubbing known inputs and credential-shaped environment values, withholding secret-looking lines); `Error:`/`Warning:` lines become findings. Validate parses the first JSON document that starts a line (skipping preceding plain text); snippets are not decoded; file names are kept only when `filepath.IsLocal`. No readable JSON and no specific failure category → one rerun with `validate -no-color`, parsed from human output (`on FILE line N` attaches locations). `fmt -check` paths are shown only when they are in the enumerated set; others are counted as hidden. `providers` output is parsed as a tree (four columns per level, `module.NAME` nesting, `provider[SOURCE] CONSTRAINT`), sources and constraints pattern-checked.

**Outcome.** `ToolResult.outcome` is `passed`, `findings` (validate invalid: `validation_errors`; files to format: `unformatted`) or `not_checked`. Status is `succeeded` only for `passed`; findings and failures are `failed`; cancel/shutdown `cancelled`. Validate is `not_checked` (and `valid` absent) when the diagnostics say init is needed, plugins are missing or mismatched, the engine version does not match or flags are unsupported, so "not valid" is never claimed for a check that could not run. A failed `providers` keeps what it printed with `partial: true`. Cancel and timeout discard partial output. Codes: `unsafe_cli_args`, `engine_version`, `path_changed`, `init_required`, `plugins_missing`, `version_mismatch`, `workspace_missing`, `state_locked`, `credentials`, `network`, `unsupported_flag`, `output_unreadable`, `output_too_large`, `format_error`, `tool_failed`, `cancelled`, `timeout`, `shutdown`.

**History.** `GET /projects/{id}/operations` lists the project's init, workspace and tool operations, newest first, from the in-memory `Inits` runner. Their redacted metadata is also recorded in [operation history](#operation-history).

### Execution profiles

**Store.** `internal/profiles.Store` keeps `profiles.json` beside `projects.json`: `{"version":1,"profiles":[{id, project_id, name, engine, workspace, var_files, options:{parallelism, lock_timeout_seconds}, aws_profile, aws_region, env_names, revision, created_at, updated_at}],"defaults":{<project id>: <profile id>}}`. Writes, re-reads, corrupt-file recovery and newer-schema read-only behavior are the registry's. Decoding refuses unknown fields, so a value field cannot be smuggled in by editing the file. Every profile belongs to one project ID; `Get`, `Update`, `Delete`, `Clone` and `SetDefault` match both IDs, so a profile ID from another project is "not found" even with the same name. `Update` and `Delete` take the expected revision (`ErrRevision` otherwise); each update increments it. Validation: names 1–60 characters without control/format characters and not credential-shaped (`state.LooksSecret`); engine `""|terraform|tofu`; workspace per `engine.ValidWorkspace`; at most 16 variable files per `engine.ValidVarFilePath` (relative, slash-separated, at most five segments, each `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`, `.tfvars`/`.tfvars.json`, not root-level auto-loaded files); parallelism 0–256 and lock timeout 0–3600 s (0 = engine default); AWS profile `^[A-Za-z0-9][A-Za-z0-9_.+=@,-]{0,63}$` and not secret-looking; AWS region `^[a-z]{2}(-[a-z]+)+-[0-9]{1,2}$`; at most 16 environment names `^[A-Za-z_][A-Za-z0-9_]{0,63}$`, no `=`, none of the names Hclaro controls (`TF_CLI_ARGS*`, `TF_LOG*`, `TF_WORKSPACE`, `TF_DATA_DIR`, `TF_IN_AUTOMATION`, `CHECKPOINT_DISABLE`, `AWS_PROFILE`, `AWS_DEFAULT_PROFILE`, `AWS_REGION`, `AWS_DEFAULT_REGION`). Removing a project removes its profiles (best effort).

**Variable files.** `ResolveVarFile(root, ref)` canonicalizes the root, `Lstat`s and `EvalSymlinks` the reference, and requires the target to be a regular file whose root-relative path is itself a valid, non-auto-loaded variable file path (so a link may not leave the root or point into a hidden folder). Errors are `var_file_missing`, `var_file_outside_root`, `var_file_not_regular`, `var_file_unreadable`, `var_file_invalid`, each with an actionable message. The API refuses such references when a profile is saved, and every resolution before an operation repeats the check. `Candidates` walks the root (five levels, hidden folders and `node_modules` skipped, 20,000 entries, 500 files) and returns only references that resolve. The engine always receives the canonical path, so the plan fingerprint's configuration walk covers its content.

**Resolution.** `Resolve(profile, root, environ)` returns `Resolved`: project, profile ID, name and revision, engine preference, workspace selector, resolved variable files, options, AWS aliases, for each expected name whether it is set (`EnvStatus`, no value), `identity: "not_verified"`, notices and issues. Issues block every profile-bound operation: a variable file error, a missing expected name (`env_missing`) and unsafe inherited flags (`unsafe_cli_args`). The **context fingerprint** is SHA-256 over the project, profile, revision and every resolved field, including issue codes. `Compose(base, resolved)` builds the child environment: refuse when any `TF_CLI_ARGS*` (case-insensitive) holds a flag other than `-no-color`; drop `TF_WORKSPACE`, `TF_LOG*`, `TF_CLI_ARGS*`; with an AWS profile drop `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`, `AWS_SECURITY_TOKEN`, `AWS_PROFILE`, `AWS_DEFAULT_PROFILE`; with a region drop `AWS_REGION`/`AWS_DEFAULT_REGION`; then add only `AWS_PROFILE`, `AWS_REGION`, `AWS_DEFAULT_REGION`. The workspace is set by the engine adapter (`SelectedWorkspace`), never through `Compose`. `engine.CLI` compares `TF_CLI_ARGS`, `TF_CLI_ARGS_<command>`, `TF_WORKSPACE` and `TF_LOG*` names without case as well. Nothing calls a cloud API; identity verification is not implemented.

**Binding.** `operations.ExecutionContext` is the sanitized copy recorded on operations, plans and approvals (no environment values; the map from reference to canonical path is unexported). `Hub.execution(project, profileID)` resolves, refuses any issue (`ProfileRefusal`) and returns the profile's engine preference (else the project's), the composed environment and the context; without a profile it returns nil, and every path behaves exactly as before.

- **Launch plans, replacements and imports.** `GET /plans/options?profileId=` returns the launch project's Hub ID and an execution summary; a profile that prefers another engine than the launch engine (`profile_engine`) or selects another workspace than the launch snapshot (`profile_workspace`) gets a blocking issue. `POST /plans` and `POST /imports` take `profileId` and `contextFingerprint`. `Manager.StartPlanWith` calls `Binder` (`Hub.LaunchBinder`, which requires the launch root to be registered) under the manager lock and refuses a missing or different fingerprint (`context_changed`), engine or workspace mismatches, and any `RejectError` from the binder. Variable files may then name root files or the profile's approved references; references become canonical paths. The operation keeps the context and the composed environment; `Manager.Bind` gives it a copy of the launch `engine.CLI` with that environment and `SelectedWorkspace` = the snapshot workspace (`CLI.WithEnvironment`), so the `workspace show` check, plan, `show -json` and later apply all run with an explicit `TF_WORKSPACE` instead of the inherited one. Options add `-parallelism=N` and `-lock-timeout=Ns` (validated again in `planArgs`). The plan fingerprint uses the composed environment and the context fingerprint.
- **Apply.** The retained artifact keeps the plan's composed environment and context. `ContextStatus`, `Approve` and `StartApply` resolve the profile again; a missing profile, any fingerprint difference or a resolution error makes the plan `context_changed` with "The execution profile … was changed or removed", which also invalidates an issued approval token (it is consumed on use and the checks run again). The apply runs with the stored environment, never a newly composed one.
- **Hub read contexts.** `POST /contexts` takes `profileId`. A profile with a workspace selector can open only that workspace (`profile_workspace`). The engine factory receives the composed environment and the profile's engine preference; the context key includes the profile ID and fingerprint, so two tabs of one project and workspace with different profiles get different contexts and stores. `Context.executionContext` is returned. Editing or deleting a profile through the API closes its contexts (`profile_changed`, `profile_removed`).
- **Tools** run with the context's profile: `StartTool` resolves it again and refuses with `context_changed` if the fingerprint differs (for example after an edit by another Hclaro process); the operation records the context.
- **Init and workspace commands.** `GET /init-status?profileId=` and `POST /workspaces/review {…, profileId}` resolve the profile; the init context ID and the workspace review's static hash include its fingerprint, and the composed environment replaces `os.Environ()` for the engine. `POST /operations/init` and `/operations/workspace` must name the same profile (`context_changed` otherwise). The inherited `TF_WORKSPACE` check for delete still uses Hclaro's own environment.

A running operation holds its own copy of the context and environment; editing or deleting the profile during the run changes neither (`TestProfileDeletedWhileRunningKeepsSnapshot`).

**Client.** `useProfileSelection(projectId)` keeps the tab's choice in `sessionStorage` (`hclaro.profile.<projectId>`, a profile ID or `none`); with nothing stored the project's default applies, and a stored ID that no longer exists falls back to none. The selector appears in the context bar (Hub workspace tabs and the registered launch project) and on the project page; choosing a profile with a workspace selector navigates the Hub tab to that workspace. `ContextSummary` renders the execution summary in the plan and import dialogs (which send the fingerprint and are disabled while issues exist); init and workspace reviews, plan review, apply confirmation and the tools view show the recorded context. Every context shows **Identity not verified**.

### Workspace comparison

A comparison has two **targets**, each `{projectId, workspace, profileId?}`, and up to 50 **rules**. It is built entirely on read contexts: the server never reads state files itself.

**Start.** `POST /api/v1/comparisons {left, right, rules, reload, acknowledgeStateRead: true}` (unknown fields refused). `compare.Validate` checks the rules first and refuses with `invalid_rule` (`index`, reason prefixed `Rule N:`): kinds `map` (`left`/`right` address prefixes: a module path, optionally followed by `TYPE.NAME` or `data.TYPE.NAME` with an optional instance key, parsed quote-aware), `ignore` (`path` pattern, optional `resourceType`) and `substitute` (`left`/`right` tokens, 1–128 characters, optional `path` and `resourceType`). Every string is at most 256 printable characters (no format characters) and is refused when `state.LooksSecret` flags it, so a rule can neither carry nor probe a secret. Targets must have 32-hex IDs and valid workspace names, and must differ (`same_target`). Then `Hub.OpenWith` runs for each side, exactly as `POST /contexts` (with `reload` closing an open context of the same tuple). An open failure is recorded on that side (`project_not_found`, `project_unavailable`, `project_busy`, `shared_data_dir`, a profile refusal) instead of failing the request. The record holds the targets, the rules and the two context IDs; at most eight are kept, for 12 hours, in memory only.

**View.** Every `GET` recomputes each side from its context without running anything: a closed context (reason `reloaded`, `evicted`, `project_removed`, `project_changed`, `initialized`, `workspace_deleted`, `profile_changed`, `profile_removed`), a project whose canonical root changed, or a profile whose fingerprint no longer matches the context's (for example after another Hclaro process edited it) makes the comparison `stale`; a snapshot still loading makes it `reading` (until both sides settle, even if the other already failed); then a snapshot in `error` (uninitialized, missing workspace, backend, credentials, `path_changed`, …) or a side that never opened makes it `partial`. Stale and partial comparisons are `withheld`: no summary, modules, providers or resources, and the resource and export routes answer 409 `comparison_stale` / `comparison_partial` (`comparison_not_ready` while reading). An `empty` snapshot (no state recorded) is a valid side. When both sides are `ready`/`empty`, `compare.Compare` runs once per pair of context IDs and capture times and is cached on the record.

**Matching.** Right instances are indexed by address. Each left address takes the first mapping rule whose left prefix matches at a segment boundary (end, `.` or `[`; an indexed prefix does not match a longer index), and is rewritten to the right prefix. Identical, unmapped addresses claim their right instance first; a mapped address that lands on an already claimed one is `uncomparable` with a warning naming the rule, never paired by guess. Unclaimed instances are `only-left` / `only-right`; a mapping rule that matched nothing is reported. A pair is `uncomparable` when mode, type or provider differs (provider compared without the `registry.terraform.io/` or `registry.opentofu.org/` host, with a note when only the host differs) or when one side's attributes are withheld as a whole.

**Attributes.** Both redacted attribute trees are walked together (maps by sorted key, lists by index, depth 32, at most 2,000 rows). A path matching an ignore rule (pattern segments `name`, `["quoted"]`, `[N]`, `*`/`[*]`; a pattern matches the path or an ancestor) is `ignored` and carries no values. A value that is `[redacted]` on either side, or contains a redacted value or a `[redacted key]`, is `sensitive` and is never compared. Equal leaves are `same`; unequal strings that become equal after a substitution rule (`strings.ReplaceAll(left, token, replacement)`) are `same` with `normalized`; other differences are `different`, `only-left` or `only-right`. Classification: any difference → `attribute-different`; otherwise any sensitive value (or truncation) → `unknown` (equality cannot be confirmed); otherwise `same`. Rule hits are counted per rule. Match IDs are `sha256("L\0" + left + "\0R\0" + right)[:16]`, so they are scoped by the comparison ID that serves them; `leftId`/`rightId` are the explorer IDs of each context, used for **Open in left/right workspace** (`/projects/<id>/workspaces/<ws>/resources?resource=<id>&profile=<id|none>`; the client reads both parameters once, seeds the tab's profile choice and removes them from the address bar).

**Modules and providers.** Module rows union the left module paths (mapped through the mapping rules) and the right ones, with direct instance counts per side and per-status counts. Provider rows union normalized sources with per-side counts and notes; state has no provider versions or aliases, so none are reported.

**Export.** `GET …/export?format=json|markdown` (attachment) contains both identities (alias, workspace, profile name, engine, version, backend, read time), the rules, the summary, warnings and, per instance, status, mode, type, addresses, mapping rule, reason, counts and differing attribute paths. It never contains attribute values or the canonical root paths. Markdown code spans are fenced so that address text cannot close them; `|` is escaped.

**Target status.** `GET /api/v1/comparisons/target?projectId&workspace&profileId` returns the project summary and, if a context with that project, workspace and profile is open, its snapshot status, capture time, engine, version and execution context. It runs no command.

### Operation history

`internal/history` keeps one JSON file, `history.json`, in the configuration directory. It is fed by an `operations.Recorder` that both runners call: the launch `Manager` (plans, applies, drift scans, graphs) and the Hub `Inits` runner (initializations, workspace commands, tools). Each operation is recorded twice, synchronously and in order: when it starts (status `running`, with the session ID and the Git commit) and when it ends (final status, outcome, log tail). The record is built only from data the runner already exposes (`Operation`, the redacted `plan.Review`, the drift summary and sanitized log events); raw output, plan files, state and environment values never reach it. History does not run, track or re-run processes.

**Conversion.** `convert` maps a record to a `HistoryEntry`: kind (`plan`, `replace`, `import`, `apply`, `drift`, `graph`, `init`, `workspace`, `tool`), status (`running`, `succeeded`, `failed`, `cancelled`, `unknown`), engine and version, project, workspace, profile name/revision and a 12-character fingerprint, redacted argv, diagnostic, Git identity, a `PlanSummary` (counts without `no-op`, up to 300 `{address, action}` pairs, output and drift counts, variable file names, replace/import addresses, fingerprint) and an `Outcome`. Projects are named by Hub ID and alias (`Hub.UseHistory` resolves roots against the registry) or, outside the Hub, by an ID derived from the root and the folder name; the path is not stored. Every string passes `clean`: control characters removed, length bounded, and any value matching `state.Suspicious` replaced by a withheld marker (addresses by `[redacted address]`). This is a second line of defense after the runner's own sanitizing, which already scrubs known variable values and secret-shaped lines.

**Outcomes.** Planned changes and execution are separate. A plan's outcome is `planned` (or `not_planned`); an apply's is `applied`, `partial` (engine started and did not finish cleanly: cancelled, failed after starting, or stopped) or `not_applied`, with `verified` always false. When an apply ends, the plan it used gets an `execution` link `{operationId, status, result}`. Drift results map to the scan outcome (`partial` for incomplete scans); init, workspace and tool results distinguish `completed`, `unverified`, `partial` and `not_run`. An entry still `running` when another process opens the file was interrupted: it becomes `unknown` / `interrupted`, with the risk wording for its kind. A concurrently running process's entry may be marked this way too; its own final record replaces it.

**Storage.** Schema 1: `{version, retention, entries}`; strict decoding (unknown fields refused). Writes go to a private temp file in the same folder, are synced and renamed; leftover temp files from an interrupted write are removed at the next start. An undecodable file is moved aside; a newer schema is left untouched and makes history read-only; invalid entries (bad ID, kind, status, time) are dropped individually and every string of a loaded entry is cleaned again, so a hand-edited file cannot inject a secret-shaped value. Older schemas upgrade through a chain of `Migration` functions keyed by version (empty today; tested with a synthetic schema 0). Each change re-reads the file when its size or modification time changed, so two processes merge entries. Retention removes entries older than `maxAgeDays`, then the oldest until at most `maxEntries` remain and the encoded file fits in `maxBytes`; running entries are never removed.

**Routes.** `GET /history` (filters `projectId`, `workspace`, `kind`, `status`, `query`; `offset`/`limit`; unknown parameters refused; list entries carry no log lines; project/workspace facets come from the whole history; `live` says whether this session still holds the full log), `GET /history/{id}`, `GET /history/compare?left=&right=` (409 `plans_incompatible` unless both are plans of the same project, workspace and engine; notices for engine version and fingerprint differences), `GET /history/export?format=json|markdown` (same filters; a download attachment; log lines and session markers dropped; `omitted` lists what was left out; Markdown control characters escaped), `PATCH /history/retention`, `DELETE /history/{id}` and `DELETE /history {confirm: true, projectId?, workspace?}` (running entries are refused or kept). Deleting only rewrites the history file. No route accepts a file path; the server-side export path exists only as the `--export-history` command-line flag, which requires a new `.json`/`.md` file in an existing folder outside `.terraform`/`.git`, refuses links and existing files and writes with `O_EXCL` and `0600`.

**No replay.** History holds no plan file, approval token or environment; plan IDs in history resolve to nothing in a new session, so `/plans/{id}`, approval and apply return 404.

### Client

The UI routes are `/projects`, `/projects/<id>`, `/projects/<id>/workspaces/<name>/<resources|overview|modules|providers|tools|git>`, `/compare` and `/history`; the server serves the app shell only for paths matching exactly that shape (32-hex ID, workspace-name pattern) and 404s everything else as before. The client parses the same shape, percent-encodes segments and never sends a path from the URL; it sends the project ID and workspace name in a POST body, and the server resolves both. Each project/workspace gets its own `Workbench` instance (React `key`) and query keys that include the context ID, so filters, selections and cached resources cannot carry over. A new tab receives the session credential in its URL fragment, like the launch URL, because sessionStorage is per tab.

List parameters: `query`, exact `module`, `provider`, `type`, `mode`, `sort=asc|desc`, `offset`, `limit`. An absent module filter means all modules; `module=` selects root resources. Queries search full address, name, provider, type and module. Details use an ID map; no raw address becomes a command argument.

The guard accepts only the exact bound authority and, when present, the exact matching Origin. Cross-site fetch metadata is refused, no CORS headers are emitted and queries are bounded. GET/HEAD requests may not carry bodies. POST is accepted only on the launch reload, plan, drift scan, apply, cancel, import, project, browse, inspect, init, workspace review, workspace command, project tool, execution profile (create, clone, default), context, comparison, Git status/diff and editor routes above, and PATCH and DELETE only on `/api/v1/projects/{id}` and `/api/v1/projects/{id}/execution-profiles/{pid}`; each additionally requires: an `Origin` header equal to the bound origin, `Sec-Fetch-Site` absent or `same-origin`, `Content-Type: application/json`, an `X-Hclaro-CSRF` header matching the per-launch CSRF token (constant-time compare), a non-empty body of at most 16 KiB, and strict JSON decoding with unknown fields rejected. Every other method/path combination returns 405. Unknown API paths cannot fall back to SPA HTML. HTTP header/body/idle/write limits bound requests. Assets cannot be directory-listed. CSP permits only local scripts/styles/fonts/connections and denies framing/forms; referrers and caching are disabled.

A private launch fragment bootstraps bearer authorization. The UI removes it from history immediately, keeps the token in sessionStorage for reload, and sends it only in headers. The token expires when the process stops; new launches use independent tokens. No cookies are used. Because the bearer token is never sent automatically by a browser, cross-site requests cannot authenticate; the CSRF header and Origin checks are additional, independent defenses for the mutating routes.

SSE streams are read with `fetch` (not `EventSource`) so the bearer token stays in a header. Request contexts derive from the server lifetime, so open streams end on shutdown; each event extends the write deadline.

## Frontend and performance

The UI requests workspace status while loading, then uses the immutable snapshot. TanStack Query caches reads without focus/reconnect refresh. Search is debounced 180 ms, filters compose on the server, and resource pages render at most 50 rows. This bounds DOM work independently of total instances. Only selected details are downloaded. Resource selection stays mounted during detail changes, preserving list scroll. Module/attribute structures use native disclosures, resource buttons support arrow navigation, and reduced-motion preferences are respected.

No runtime fonts, CDNs, analytics or hosted APIs are used. Display preferences are validated before use and are the only localStorage data. The sidebar, dashboard, modules and providers all derive from real snapshot counts.

The Resources view adds a checkbox to managed rows only; the selection (kept across pages and filters, at most 50) opens the replace preflight, which lists the exact addresses. The Plans view shows plan availability, a preflight dialog (providers and backend contacted, possible state lock, no infrastructure change), the live operation log with cancel, failures with sanitized diagnostics, and the review: metadata, for replacements the requested instances next to a count of every other change, apply status (ready with expiry, or the reason it is review only), action counts that double as filters, the complete change list (no-ops behind a toggle, 200 rows per page), a change inspector with attribute diff, outputs, and drift. The apply dialog requests the approval when it opens, shows counts, command and digest, and keeps **Apply plan** disabled until the typed phrase matches; Cancel has initial focus. After an apply the explorer queries are invalidated and the outcome is shown separately from the exit status. Actions are distinguished by icon and text, not color alone. The Operations view lists session plans and applies and replays retained logs. The Import view is a single page with numbered steps: the request form, the server preview (issues, configuration status, the new file as an added-lines diff, a manual recipe), and, only when nothing blocks, a consent checkbox before **Write file and plan import**. Any edit discards the preview. Import plans get a summary of the target, other changes and the redacted generated configuration; failures show recovery steps.

The build is TypeScript + Vite + Tailwind, with React, TanStack Query, Lucide and a shadcn-style Button. Vite writes content-hashed files to `internal/ui/dist/assets/` plus `THIRD-PARTY-NOTICES.txt` for runtime dependencies; the Go binary embeds that directory. `scripts/build-offline-preview.mjs` remains only as a no-network fallback and must not be committed as release assets.
