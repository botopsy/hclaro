# Security policy

This policy covers hclaro, published by BotOpsy.

## Reporting a vulnerability

Please report security problems **privately**. Do not open a public issue, discussion or pull request for them.

- Preferred: GitHub private vulnerability reporting, **Security → Report a vulnerability** on the repository (<https://github.com/botopsy/hclaro/security/advisories/new>).
- If that form is not available, start a [Q&A discussion](https://github.com/botopsy/hclaro/discussions/new?category=q-a) titled "Requesting a private security contact" with no details in it, and BotOpsy will reply with a private channel. Do not use the issue forms for this: they ask for reproduction steps.

Include the Hclaro version (`hclaro --version`), OS, engine and version, and steps to reproduce with **synthetic** data. Never send real credentials, state, plans, plan output, `.tfvars` contents, the private session URL or real account identifiers; describe them or use placeholders instead. If you believe a secret was exposed, rotate it first.

Only the latest beta release receives security fixes. There is no bug bounty.

## Security design

Launch is read-only. Since M2, a user can explicitly start a **plan**, which contacts providers and the backend and may lock the state, but never writes state or infrastructure. Since M3, a user can **apply a reviewed saved plan** for a locally executed workspace after a one-time, plan-bound confirmation; this changes infrastructure and state. Since M4, a user can **write an import block to a new project file** after previewing it and consenting, which starts a normal plan; the import is recorded only by applying that reviewed plan. Since M5, the Workspace Hub registers project folders and reads their CLI workspaces read-only; it never selects or creates workspaces. Since M6, a user can explicitly run a standard **init** for one Hub project after reviewing it; init writes the project's data directory and lock file and can contact registries and the backend, but never upgrades, migrates or reconfigures. Since M7, a user can explicitly create a CLI workspace, set the CLI default or delete an empty workspace (local backend only) after a review; there is no `-force`. Since M8, a user can run four read-only project tools in a Hub workspace (`validate`, `fmt -check`, `providers`, `output -json` reduced to metadata); none writes configuration or state. There is no `import` command, destroy, state-edit, unlock or generic executor API, and no way to apply anything other than the reviewed saved file. Development and CI use only synthetic fixtures and fake engines.

### Protected boundaries

- Bind exclusively to 127.0.0.1; exact Host and Origin validation, cross-site fetch rejection, no wildcard CORS.
- Random per-launch bearer authorization for every API, including health. The private URL uses a fragment, not an HTTP query credential.
- GET/HEAD for every read route; bodies rejected; bounded queries, headers, request duration, engine output and parsing depth.
- Mutating routes are an explicit list: the launch project's reread (`workspace/reload`, which runs only the startup reads), nine plan/drift/graph/apply/import POSTs (start plan, start a drift scan, generate a dependency graph, run an apply preflight, approve a plan, apply an approved plan, cancel operation, preview an import, start an import), the Workspace Hub POSTs (register, order, inspect and browse projects, open a read context, start a workspace comparison, start an init, review and start a workspace command, start one of the four project tools) PATCH/DELETE of one Hub project or execution profile, and the operation history's retention PATCH and entry/clear DELETEs. Each requires the exact Origin, same-origin fetch metadata when present, JSON content type, a per-launch CSRF header, a body of at most 16 KiB and strict decoding; plans also need an explicit backend-access acknowledgement.
- Hub scoped execution (M24.03–M24.09, hidden `--experimental-hub-execution`, off by default): plan, import, drift scan, graph, AWS discovery, preflight, approval, apply and cancel routes under `/api/v1/contexts/{cid}/…` act only on that open context's pinned root, engine, workspace and profile, and never fall back to the launch project. Each request revalidates the scope; an import revalidates again with the root claim held before writing, and its preview digest is bound to the context, so a reviewed block cannot be written into another project or workspace. Imports and replacements are full plans (no `-target`, no `terraform import`, no state edits) applied only through the reviewed saved-plan approval.
- Workspace Hub: the registry stores only IDs, canonical paths, names, engine choice, pins and last-opened metadata, in a `0600` file written atomically; an undecodable file is moved aside and a newer or unreadable one is never overwritten. Paths are absolute, symlink-resolved, checked for project files and deduplicated by identity; the folder chooser lists one folder's subdirectory names, never files and never recursively. Routes take project IDs and workspace names, never paths from a URL; workspace names are pattern-checked. Hub workspaces are read-only: their engine wrapper exposes only `version`, `workspace` and `show`, each child gets its own `TF_WORKSPACE`, Hclaro's environment is never changed and reading or switching a workspace never runs `workspace select`/`new`/`delete`. The engine must report the selected workspace before state is read; an absolute (shared) `TF_DATA_DIR` refuses Hub reads. Unregistering or changing a project closes its contexts and cancels reads; a context only serves its own snapshot.
- Init (M6): the only argv is `init -input=false -no-color` (or `-json` instead of `-no-color` for Terraform ≥ 1.9), built by the server; the request carries only `mode: "standard"` and the context ID from the review, and unknown fields such as arguments or backend values are refused. `TF_CLI_ARGS`/`TF_CLI_ARGS_init` with anything but `-no-color` refuses init; `TF_WORKSPACE` and `TF_LOG*` are dropped. The context ID hashes the project, canonical root, engine choice, executable path and identity, configuration and data-directory fingerprint (including the lock file) and `TF_*` environment; it is rechecked when init is requested and again just before the engine starts, together with the root and executable identity, so a changed or symlink-swapped root is refused. The environment is pinned at request time. One operation per project root at a time, shared with the launch project's plan/apply/import. The engine runs in its own process group; cancel interrupts the group and kills it after 15 seconds. stdout and stderr are sanitized line by line before entering the bounded log: known inputs and values of credential-shaped variables (`*SECRET*`, `*TOKEN*`, `*ACCESS_KEY*`, `TF_TOKEN_*` and similar) are replaced, credential-shaped lines withheld. Failures are classified, never retried.
- Workspace commands (M7): the only argv is `workspace new|select|delete NAME`, built by the server; names must start with a letter or digit (`^[A-Za-z0-9][A-Za-z0-9_-]{0,89}$`), so no name can become a flag, and unknown request fields (such as `force` or `args`) are refused. `TF_WORKSPACE` and `TF_LOG*` are dropped; `TF_CLI_ARGS`, `TF_CLI_ARGS_show`, `TF_CLI_ARGS_workspace` or the full-subcommand variable the engines read (`TF_CLI_ARGS_workspace_list`, `TF_CLI_ARGS_workspace_<action>`) with anything but `-no-color` refuse. A start must present a server-kept, single-use review (10 minutes) for the same project, action and name; the root, executable, configuration fingerprint, backend metadata and `TF_*` environment must be unchanged, and a fresh `workspace list` must equal the reviewed one before the command runs. Delete requires the local backend, a non-default workspace that is neither the CLI default nor the inherited `TF_WORKSPACE`, and recorded state with no resource instances or outputs (read twice); the engine's own non-force check is a third guard. Output is sanitized like init. Unconfirmed results are reported as `unknown` and never retried or undone.
- Project tools (M8): the argv is one of `validate -json`, `validate -no-color` (fallback), `fmt -check -no-color [-recursive]`, `providers` and `output -json`, built by the server from the route; the body may contain only an open context ID and, for format check, `recursive`. The context pins project, root, engine executable (checked by path and file identity) and workspace; `providers` and `output` get that workspace as child `TF_WORKSPACE`, the others none, and inherited `TF_WORKSPACE` and `TF_LOG*` are dropped. `TF_CLI_ARGS`/`TF_CLI_ARGS_<command>`/`TF_CLI_ARGS_version` with anything but `-no-color` refuse. `output -json` is decoded into names, types and `sensitive` flags only; values are never decoded, stored or returned, its stdout is never logged and its stderr is used only for a failure category. Object attribute names in output types are counted, not shown, and output names that look like secrets are hidden. Validate snippets are never decoded; diagnostic text and every log line are sanitized like init, and file names are shown only when they are plain paths inside the root. Format check is check-only; Hclaro enumerates the files it reads beforehand, shows only listed paths, never follows linked folders and refuses linked files outside the root. Tools take a shared root claim, never concurrent with init, workspace commands or plans in that root. History is in memory only.
- Execution profiles (M9): `profiles.json` (schema 1, `0600`, atomic, strict decoding that refuses unknown fields) stores per-project names only: engine preference, workspace selector, approved variable file paths, `-parallelism`/`-lock-timeout` values, an AWS profile alias and region, and expected environment variable names. Names, AWS profiles and variable file paths that look like credentials are refused; Hclaro-controlled names (`TF_CLI_ARGS*`, `TF_WORKSPACE`, `TF_LOG*`, `AWS_PROFILE`, …) cannot be listed. Variable files are resolved through symbolic links to their canonical path, which must stay inside the canonical project root and outside hidden folders, at save time and again before each operation; contents are never read or returned. A profile-bound child environment is the inherited one minus `TF_WORKSPACE`, `TF_LOG*` and `TF_CLI_ARGS*` (any unsafe `TF_CLI_ARGS*` refuses, compared without case), minus inherited static AWS credentials when an AWS profile is chosen, plus only `AWS_PROFILE`/`AWS_REGION`/`AWS_DEFAULT_REGION`; it lives in memory for the operation and its saved plan and is never serialized. Operations, plans and approvals record the sanitized context and its fingerprint (project, profile, revision and resolved fields); approval and apply re-resolve the profile and refuse any change. The account behind an AWS profile is never looked up, and the UI labels it as not verified. The selected profile is per browser tab (`sessionStorage`).
- Apply preflight (M14): an approval needs the binding of a server-side preflight with no blocking check (256 bits, ten minutes, replaced by each new preflight) and the exact list of warning check IDs to acknowledge; the whole preflight is evaluated again when the apply starts and any new blocker or unacknowledged warning refuses it. Context, fingerprint, profile, digest, expiry, engine support, backend execution mode, local operation conflicts and policy validity always block; unknown is never pass. `.hclaro/policy.json` is strict data (version 1, 64 KiB, no symlinks, no code or URLs) and cannot relax those checks. The Git probe is a fixed argv `git status --porcelain=v1 -z` run through the Git context runner below: `core.fsmonitor` and the untracked cache disabled, optional locks off, no prompts, every inherited `GIT_*` variable removed, a timeout and stderr discarded. The AWS identity probe (`aws sts get-caller-identity`) runs only on an explicit request, with the plan's environment, the pager and prompts off and stderr discarded; only the account and a validated ARN are kept. Preflight evidence, Git paths, account IDs and ARNs are returned only in the preflight response, never logged or recorded in history.
- Unsupported plan actions (M24.01): any resource or output change whose action list is not one of the recognized combinations ([docs/plan-actions.md](docs/plan-actions.md)) makes the plan ineligible. Its saved file is not kept, approval and apply are refused with `unknown_actions` (a destructive confirmation cannot override this), and the check is repeated from the recorded action lists immediately before the engine would start.
- Apply needs a one-time token issued for that plan (256 bits, five minutes, invalidated by any use) and, for plans that delete, replace or forget objects, a typed phrase. The server re-checks the context fingerprint, engine version, workspace, plan age and the saved file's SHA-256 before running `apply` on that file only. Replacement targets are opaque IDs resolved to managed instance addresses from state, each passed as a single argv element.
- Imports: the address is parsed into a strict subset (no quotes, backslashes or template sequences in keys) and the ID is written as an escaped HCL string (`${`/`%{` doubled), so neither can inject configuration. Credential-shaped IDs are refused. The start request must carry the SHA-256 of the previewed content and destination and two acknowledgements; every check is repeated before writing. The file is a new bare `.tf` name in the root (no override files), created via a temporary file and a hard link that fails if anything exists at the name; a symlinked destination or swapped project directory is refused. `-generate-config-out` takes only a derived bare file name. Engine-generated configuration is returned only as a redacted display copy. Hclaro never deletes user files.
- Drift scans (M10): fixed argv `plan -input=false -json -out=<private file> -refresh-only` (plus server-validated variable files and profile options); `-refresh-only` cannot be combined with `-replace` or `-generate-config-out`, and the request body may contain only the acknowledgement, variable files, profile ID and context fingerprint. The refresh-only plan file is written to a private `0700` temp directory and always deleted after `show -json`; it is never retained, listed as a plan or passed to `apply`, and no `refresh`, `apply -refresh-only` or state command exists in the engine adapter. Results reuse the plan redaction (sensitive markers, secret-like names, credential-shaped values even when a provider does not flag them) and are kept in memory only, at most ten for 12 hours. A scan is bound to the workspace, engine, version and context fingerprint it ran with; any difference withholds its resources and refuses its details. A document that proposes resource changes is refused as not refresh-only. "No drift" is reported only for a complete scan without error diagnostics.
- Dependency graphs (M11): fixed argv `graph` with no arguments; the body may contain only the acknowledgement, profile ID and context fingerprint, so no saved plan, path, `-type` or other flag can reach the engine, and `TF_CLI_ARGS_graph` is held to `-no-color`. Stdout is capped at 16 MiB and stderr is never returned. The DOT parser is bounded (bytes, nodes, edges, nesting, identifier length) and fails closed. Only a parsed model is kept: node names flagged by the secret heuristics are replaced by `[redacted node]`, DOT labels and attributes are discarded, and graphs live in memory only (five, 12 hours) bound to the workspace, engine, version and context fingerprint; a stale graph's nodes are withheld. Graph nodes are mapped to recorded instances only by exact address grammar. A plan is overlaid only when it is complete and current, and the UI never presents a dependency link as the cause of a planned change. No graph route can plan, refresh, apply or target anything.
- Operation history (M13): `history.json` (schema 1, `0600` in a `0700` folder, atomic writes, strict decoding) keeps redacted metadata only: kind, status, times, engine/version, project ID and alias or folder name (never the path), workspace, profile name, a short context fingerprint, the redacted argv, diagnostic, Git commit/branch, at most 40 sanitized log lines and, for plans, counts and up to 300 `{address, action}` pairs. Plan files, state, attribute/output/variable values, environment values and raw output are never written; every string is checked again with the secret-shape heuristics before writing and after reading, so a value that looks like a credential is withheld. A historical plan has no artifact and can never be approved or applied. Exports (download or `--export-history`) omit log lines and say what was omitted; the server never accepts an export path from the browser, and the command-line export writes only new `.json`/`.md` files (`O_EXCL`, `0600`, links and `.terraform`/`.git` refused). History routes are GET except `PATCH /history/retention` and `DELETE /history[/{id}]`, which need the bearer token, Origin and CSRF header like every mutating route; deleting history edits only the history file. Limitation: a secret that is neither a known input nor credential-shaped (for example a short human-chosen password echoed by a provider) is not recognized, as in the live log.
- Git context (M15): Git runs only through an allowlist of three read-only subcommands (`rev-parse`, `status`, `diff`) with fixed options, as argv without a shell, with `core.fsmonitor` and the untracked cache disabled, `--no-optional-locks`, no pager, no prompts, external diff and textconv disabled, every inherited `GIT_*` variable removed, a timeout, bounded output and stderr discarded; tests record every Git command and fail on anything else. Git output is untrusted: malformed status or diff output is refused as a whole. The browser never sends a path, Git argument, executable or URL: it sends opaque file IDs (HMAC with a per-process key) that the server resolves against a fresh status or the current project scope (root and local modules from the module manifest, symlinks resolved and required to stay inside the repository and the root or a module directory). Only `.tf`/`.tf.json` diffs are returned, with secret-named literals, credential-shaped values and secret heredocs redacted server-side. Git sends the whole file as context and each side is analysed whole, so everything inside a block, list, call or heredoc opened under a secret-like name and the value of a secret name/value pair (`name = "DB_PASSWORD"` with `value = …`, on any line of the block) is hidden however far the change is from the name; a diff without full context is withheld entirely. A block whose label or name looks like a secret (`resource "aws_kms_key" "secrets"`, `module "secrets"`, `variable "db_password"`, `master_password { … }`) is hidden whole, whatever its attributes are called. Lines assigning a secret-like name are hidden whole, also inside an inline object (`tags = { token = … }`), when the name is escaped (`"p\u0061ssword"`) or when the value continues after a line ending in an operator; commented-out assignments to secret-like names and block comments are hidden. The import preview applies the same rule; `.tfvars` and lock file contents are never sent, and diffs are never logged or stored. Responses carry the repository folder name and repository-relative paths, never the absolute path. **Open in editor** accepts only `vscode` or `cursor`, validates the line, percent-encodes the path into `vscode://file/…` (or `cursor://`) and passes that single argument to the OS URL opener. Status, diff and editor routes are CSRF-protected POSTs; HEAD and source lookups are GETs that only read files. Limitation: the redaction is textual and can miss a secret under an ordinary name that does not look random, as in the state redactor.
- Cloud discovery (M16): the AWS CLI (`aws` from `PATH`, v2 only) runs through an allowlist of five read-only operations (`sts get-caller-identity`, `ec2 describe-vpcs|describe-subnets|describe-security-groups`, `s3api list-buckets`, `rds describe-db-instances`) plus `--version`, as argv without a shell, with only `--region`, `--output json`, `--max-items`, `--starting-token` (validated) and fixed pager/timeout options; `--profile`, `--endpoint-url`, `--query`, `--cli-input-json` and every create/modify/delete operation are refused before the CLI is looked up, and tests record every call. The environment is the execution profile's composed environment (or Hclaro's), with the pager, auto-prompt and CLI retries disabled; credentials are never read into Hclaro. stderr is used only to classify errors (access denied, expired SSO, throttling, …) and is never returned or logged. Responses are decoded into fixed structs: rules, policies, descriptions, endpoints and user names are never decoded; tags and names are stripped of control/bidi characters, bounded, and credential-shaped values or secret-named tags are replaced. Nothing runs on GET: verification, scans, cancel and import preparation are CSRF-protected POSTs. Verifications, scans and prepared imports are bound to the profile, its context fingerprint, the workspace and the engine; a scan of another context withholds its results, every scan and preparation re-checks the STS account, and the import route re-checks a prepared candidate (ID, type, context, expiry, single use) before writing anything. Limits are enforced server-side: at most 6 regions, 1,000 objects per type and region and 5,000 objects per scan; a list or scan that hits a limit is marked `truncated` and the scan `partial`, never complete. Only `aws_vpc`, `aws_subnet`, `aws_security_group`, `aws_s3_bucket` and `aws_db_instance` are discovered; other AWS types, Azure and Google Cloud need their own milestone and security review. Results live in memory only. Limitations: a tag value that is secret but neither secret-named nor credential-shaped is shown; AWS CLI configuration such as `credential_process` or `~/.aws/cli/alias` is the user's own and runs as it would in their terminal.
- Cost estimates (M17): off by default and unavailable with `--strict-local`. Before opt-in no process is started (the `infracost` executable is only looked up on `PATH`) and nothing is sent; opting in requires the acknowledged disclosure version and runs only `infracost --version` (v0.10 required). The only other command is `infracost breakdown --path <private file> --format json --no-color --log-level=warn`, as argv without a shell; the path must be `plan.json` directly inside a fresh `0700` `hclaro-cost-*` directory, written `0600` and deleted after every run (leftovers older than an hour are swept at startup). The browser names only a stored plan ID; paths, flags, files and keys are refused. The file is a minimized plan (`cost.Minimize`): sensitive-marked values, secret-named and free-text attributes (tags, descriptions, policies, user data, scripts…), credential-shaped, random-looking and long strings, variables, outputs, drift, checks, module sources and provider arguments other than a literal region are dropped. The child environment is an allowlist (process basics, proxy/TLS settings, `INFRACOST_API_KEY`, `INFRACOST_PRICING_API_ENDPOINT`, `INFRACOST_CURRENCY`) with update checks, Infracost Cloud and the dashboard switched off; cloud credentials, `TF_VAR_*`, Terraform Cloud tokens and profile environments are never passed. stderr is only classified and never returned. Reports are decoded into fixed structs with exact decimal arithmetic; only addresses of the reviewed plan are shown, and component names are length-bounded and withheld when credential-shaped. Only aggregates (no addresses or line items) are written to `cost-estimates.json` (`0600`, atomic). Every 12-digit number inside an attribute value (an AWS account ID in an ARN, ECR or SQS URL, bucket name or owner field) is replaced with `000000000000`; the rest of the value, including an ARN's region, is kept. Resource addresses are not changed (masking them would merge `for_each` instances), so an account ID used as a `for_each` key stays in the local input file. Limitation: Hclaro cannot inspect what the Infracost CLI itself sends to its pricing API beyond the input it is given; the pricing attributes it keeps (instance types, sizes, regions, resource IDs such as AMI IDs, resource names inside ARNs) do leave the device.
- Workspace comparisons (M12): a comparison only opens (or reuses) two Hub read contexts, so each side runs exactly the context reads (`version`, `workspace list`, `workspace show`, `show -json` with a per-command `TF_WORKSPACE` and the side's profile environment) and nothing else; the request names registered project IDs, workspace names and profile IDs, never paths or commands. Comparison runs on the already redacted snapshots: a redacted value is never compared, so equality of secrets cannot be inferred, and sensitive and ignored rows carry no values. Rules are validated (address and path grammar, printable, at most 256 characters) and refused when they look like credentials. Results live in memory only (eight, 12 hours); a side that changed (read again, released, project or profile changed) withholds every resource-level result, and a side that failed is reported as failed, never as empty. Exported reports contain identities, counts, statuses and attribute paths only: no values and no folder paths.
- Plans: fixed argv (`plan -input=false -json -out=…`), no user-supplied flags; variable files limited to a server-side list of root `*.tfvars` names; unsafe `TF_CLI_ARGS_plan` refused. One operation at a time.
- Saved plans are written only to a private `0700` OS temp directory, set to `0600`, hashed, read back and deleted immediately — and on failure, cancellation, timeout and shutdown. They are never written to the project.
- Plan values and outputs are redacted with the state policy after diffing. Progress logs are rebuilt from typed engine events; free text is sanitized line by line; stderr is never returned.
- Same-origin CSP, no framing or referrers, no external runtime assets, no raw-state endpoint.
- Redaction before snapshot publication: engine sensitivity markers at any depth, secret-like attribute names (compared without case or separators, so `privateKey` and `x-api-key` count), the value of a name/value pair whose name is secret-like (`{"name": "DB_PASSWORD", "value": …}`), strings holding JSON (also escaped) in which anything would be hidden (for example a container definition), strings that start with `{` or `[` but are not exactly one JSON document (they cannot be inspected), HTTP Basic credentials, and credential-shaped or random-looking values are hidden. Ambiguous values are hidden rather than shown, so some ordinary values (such as an IAM policy that mentions a token condition key) appear as `[redacted]`. Other values are shown, as `terraform plan` would show them.
- No raw diagnostics or state persisted by Hclaro. Child TF_LOG output and checkpoint checks are disabled; unsafe injected CLI flags fail explicitly.

### Limits

**Network access.** Hclaro itself listens only on 127.0.0.1 and makes no network requests of its own. The programs it starts do: the opt-in Infracost CLI sends the minimized plan to its pricing API (see Cost estimates above), and reading state, `init`, plan and apply load provider plugins and contact the configured backend, registries and cloud APIs with the credentials in your environment or execution profile, as they would in your terminal. The AWS CLI runs only for an explicit discovery or identity check.

**The private session URL is a credential.** Its fragment (`#session=…`) holds the bearer token for this launch. Fragments are not sent to servers or in referrers; the page moves the token to the tab's `sessionStorage` and removes it from the address bar and history at once. The terminal output and any shell history, screen recording or log that captured it still contain it. Anyone with it can use the session until Hclaro stops; stop Hclaro (Ctrl+C) to revoke it.

A local process that can inspect memory, modify executables, or read terminal/browser session credentials is outside the threat model. Existing IaC engines, provider plugins, selected directories and inherited credential configuration are trusted local inputs; state inspection can load plugins and contact the configured backend. This does not turn existing provider behavior into a security sandbox.

While a plan can be applied, its saved file stays in a private `0700` directory under the OS temp directory for up to one hour. Saved plans can contain plaintext secrets. Hclaro deletes it after an apply attempt, on expiry, when superseded and on normal shutdown; if the process is killed (for example `kill -9` or a crash), the file remains until a later Hclaro start removes it (only directories older than three hours, so another running instance's plan is never touched) or the OS cleans its temp directory. Apply runs with the user's own credentials and cannot be undone by Hclaro; an interrupted apply can leave infrastructure partly changed.

Sensitive values should not appear in resource addresses/instance keys or module/provider identifiers. No heuristic can identify every secret: a secret the provider does not mark sensitive, stored under an ordinary attribute name and not looking random (such as a short human-chosen password), is shown. Engine and provider diagnostics are free text. Known input values (`TF_VAR_*` and values from loaded variable files) are replaced and credential-shaped lines are withheld, but a secret that is neither, such as one returned by a provider API inside an error message, can still be shown. A forcefully stopped plan (after the 15-second grace period, or immediately on Windows when Hclaro has no console) can leave a state lock; Hclaro never unlocks state. Import IDs are written to configuration in plain text and are shown in the preview and in engine diagnostics; only credential-shaped IDs are refused. Configuration generated by the engine is written unredacted to the project, as the engine writes it; the display copy hides secret-like names, credential-shaped and random-looking values and heredoc bodies, but the same heuristic limits apply. Shown values are not a promise that the data is safe to share publicly. Do not share the private session URL.

Backend execution modes and unknown initialization metadata are reported conservatively. Only Terraform 1.5.5 with the local backend and the built-in `terraform_data` resource has been run for real, on macOS. No cloud provider, remote backend, OpenTofu release or other operating-system runtime has been certified. See [M01 evidence](docs/archive/verification/M01-verification.md) and [M02 evidence](docs/archive/verification/M02-verification.md).
