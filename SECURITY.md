# Security

Launch is read-only. Since M2, a user can explicitly start a **plan**, which contacts providers and the backend and may lock the state, but never writes state or infrastructure. Since M3, a user can **apply a reviewed saved plan** for a locally executed workspace after a one-time, plan-bound confirmation; this changes infrastructure and state. Since M4, a user can **write an import block to a new project file** after previewing it and consenting, which starts a normal plan; the import is recorded only by applying that reviewed plan. Since M5, the Workspace Hub registers project folders and reads their CLI workspaces read-only; it never selects or creates workspaces. Since M6, a user can explicitly run a standard **init** for one Hub project after reviewing it; init writes the project's data directory and lock file and can contact registries and the backend, but never upgrades, migrates or reconfigures. Since M7, a user can explicitly create a CLI workspace, set the CLI default or delete an empty workspace (local backend only) after a review; there is no `-force`. Since M8, a user can run four read-only project tools in a Hub workspace (`validate`, `fmt -check`, `providers`, `output -json` reduced to metadata); none writes configuration or state. There is no `import` command, destroy, state-edit, unlock or generic executor API, and no way to apply anything other than the reviewed saved file. Development and CI use only synthetic fixtures and fake engines.

## Protected boundaries

- Bind exclusively to 127.0.0.1; exact Host and Origin validation, cross-site fetch rejection, no wildcard CORS.
- Random per-launch bearer authorization for every API, including health. The private URL uses a fragment, not an HTTP query credential.
- GET/HEAD for every read route; bodies rejected; bounded queries, headers, request duration, engine output and parsing depth.
- Mutating routes are an explicit list: the launch project's reread (`workspace/reload`, which runs only the startup reads), six plan/apply/import POSTs (start plan, approve a plan, apply an approved plan, cancel operation, preview an import, start an import), the Workspace Hub POSTs (register, order, inspect and browse projects, open a read context, start an init, review and start a workspace command, start one of the four project tools) and PATCH/DELETE of one Hub project. Each requires the exact Origin, same-origin fetch metadata when present, JSON content type, a per-launch CSRF header, a body of at most 16 KiB and strict decoding; plans also need an explicit backend-access acknowledgement.
- Workspace Hub: the registry stores only IDs, canonical paths, names, engine choice, pins and last-opened metadata, in a `0600` file written atomically; an undecodable file is moved aside and a newer or unreadable one is never overwritten. Paths are absolute, symlink-resolved, checked for project files and deduplicated by identity; the folder chooser lists one folder's subdirectory names, never files and never recursively. Routes take project IDs and workspace names, never paths from a URL; workspace names are pattern-checked. Hub workspaces are read-only: their engine wrapper exposes only `version`, `workspace` and `show`, each child gets its own `TF_WORKSPACE`, Hclaro's environment is never changed and reading or switching a workspace never runs `workspace select`/`new`/`delete`. The engine must report the selected workspace before state is read; an absolute (shared) `TF_DATA_DIR` refuses Hub reads. Unregistering or changing a project closes its contexts and cancels reads; a context only serves its own snapshot.
- Init (M6): the only argv is `init -input=false -no-color` (or `-json` instead of `-no-color` for Terraform ≥ 1.9), built by the server; the request carries only `mode: "standard"` and the context ID from the review, and unknown fields such as arguments or backend values are refused. `TF_CLI_ARGS`/`TF_CLI_ARGS_init` with anything but `-no-color` refuses init; `TF_WORKSPACE` and `TF_LOG*` are dropped. The context ID hashes the project, canonical root, engine choice, executable path and identity, configuration and data-directory fingerprint (including the lock file) and `TF_*` environment; it is rechecked when init is requested and again just before the engine starts, together with the root and executable identity, so a changed or symlink-swapped root is refused. The environment is pinned at request time. One operation per project root at a time, shared with the launch project's plan/apply/import. The engine runs in its own process group; cancel interrupts the group and kills it after 15 seconds. stdout and stderr are sanitized line by line before entering the bounded log: known inputs and values of credential-shaped variables (`*SECRET*`, `*TOKEN*`, `*ACCESS_KEY*`, `TF_TOKEN_*` and similar) are replaced, credential-shaped lines withheld. Failures are classified, never retried.
- Workspace commands (M7): the only argv is `workspace new|select|delete NAME`, built by the server; names must start with a letter or digit (`^[A-Za-z0-9][A-Za-z0-9_-]{0,89}$`), so no name can become a flag, and unknown request fields (such as `force` or `args`) are refused. `TF_WORKSPACE` and `TF_LOG*` are dropped; `TF_CLI_ARGS`, `TF_CLI_ARGS_workspace` or `TF_CLI_ARGS_show` with anything but `-no-color` refuse. A start must present a server-kept, single-use review (10 minutes) for the same project, action and name; the root, executable, configuration fingerprint, backend metadata and `TF_*` environment must be unchanged, and a fresh `workspace list` must equal the reviewed one before the command runs. Delete requires the local backend, a non-default workspace that is neither the CLI default nor the inherited `TF_WORKSPACE`, and recorded state with no resource instances or outputs (read twice); the engine's own non-force check is a third guard. Output is sanitized like init. Unconfirmed results are reported as `unknown` and never retried or undone.
- Project tools (M8): the argv is one of `validate -json`, `validate -no-color` (fallback), `fmt -check -no-color [-recursive]`, `providers` and `output -json`, built by the server from the route; the body may contain only an open context ID and, for format check, `recursive`. The context pins project, root, engine executable (checked by path and file identity) and workspace; `providers` and `output` get that workspace as child `TF_WORKSPACE`, the others none, and inherited `TF_WORKSPACE` and `TF_LOG*` are dropped. `TF_CLI_ARGS`/`TF_CLI_ARGS_<command>`/`TF_CLI_ARGS_version` with anything but `-no-color` refuse. `output -json` is decoded into names, types and `sensitive` flags only; values are never decoded, stored or returned, its stdout is never logged and its stderr is used only for a failure category. Object attribute names in output types are counted, not shown, and output names that look like secrets are hidden. Validate snippets are never decoded; diagnostic text and every log line are sanitized like init, and file names are shown only when they are plain paths inside the root. Format check is check-only; Hclaro enumerates the files it reads beforehand, shows only listed paths, never follows linked folders and refuses linked files outside the root. Tools take a shared root claim, never concurrent with init, workspace commands or plans in that root. History is in memory only.
- Apply needs a one-time token issued for that plan (256 bits, five minutes, invalidated by any use) and, for plans that delete, replace or forget objects, a typed phrase. The server re-checks the context fingerprint, engine version, workspace, plan age and the saved file's SHA-256 before running `apply` on that file only. Replacement targets are opaque IDs resolved to managed instance addresses from state, each passed as a single argv element.
- Imports: the address is parsed into a strict subset (no quotes, backslashes or template sequences in keys) and the ID is written as an escaped HCL string (`${`/`%{` doubled), so neither can inject configuration. Credential-shaped IDs are refused. The start request must carry the SHA-256 of the previewed content and destination and two acknowledgements; every check is repeated before writing. The file is a new bare `.tf` name in the root (no override files), created via a temporary file and a hard link that fails if anything exists at the name; a symlinked destination or swapped project directory is refused. `-generate-config-out` takes only a derived bare file name. Engine-generated configuration is returned only as a redacted display copy. Hclaro never deletes user files.
- Plans: fixed argv (`plan -input=false -json -out=…`), no user-supplied flags; variable files limited to a server-side list of root `*.tfvars` names; unsafe `TF_CLI_ARGS_plan` refused. One operation at a time.
- Saved plans are written only to a private `0700` OS temp directory, set to `0600`, hashed, read back and deleted immediately — and on failure, cancellation, timeout and shutdown. They are never written to the project.
- Plan values and outputs are redacted with the state policy after diffing. Progress logs are rebuilt from typed engine events; free text is sanitized line by line; stderr is never returned.
- Same-origin CSP, no framing or referrers, no external runtime assets, no raw-state endpoint.
- Redaction before snapshot publication: engine sensitivity markers at any depth, secret-like attribute names, and credential-shaped or random-looking values are hidden. Other values are shown, as `terraform plan` would show them.
- No raw diagnostics or state persisted by Hclaro. Child TF_LOG output and checkpoint checks are disabled; unsafe injected CLI flags fail explicitly.

## Limits

A local process that can inspect memory, modify executables, or read terminal/browser session credentials is outside the threat model. Existing IaC engines, provider plugins, selected directories and inherited credential configuration are trusted local inputs; state inspection can load plugins and contact the configured backend. This does not turn existing provider behavior into a security sandbox.

While a plan can be applied, its saved file stays in a private `0700` directory under the OS temp directory for up to one hour. Saved plans can contain plaintext secrets. Hclaro deletes it after an apply attempt, on expiry, when superseded and on normal shutdown; if the process is killed (for example `kill -9` or a crash), the file remains until a later Hclaro start removes it (only directories older than three hours, so another running instance's plan is never touched) or the OS cleans its temp directory. Apply runs with the user's own credentials and cannot be undone by Hclaro; an interrupted apply can leave infrastructure partly changed.

Sensitive values should not appear in resource addresses/instance keys or module/provider identifiers. No heuristic can identify every secret: a secret the provider does not mark sensitive, stored under an ordinary attribute name and not looking random (such as a short human-chosen password), is shown. Engine and provider diagnostics are free text. Known input values (`TF_VAR_*` and values from loaded variable files) are replaced and credential-shaped lines are withheld, but a secret that is neither, such as one returned by a provider API inside an error message, can still be shown. A forcefully stopped plan (after the 15-second grace period, or immediately on Windows when Hclaro has no console) can leave a state lock; Hclaro never unlocks state. Import IDs are written to configuration in plain text and are shown in the preview and in engine diagnostics; only credential-shaped IDs are refused. Configuration generated by the engine is written unredacted to the project, as the engine writes it; the display copy hides secret-like names, credential-shaped and random-looking values and heredoc bodies, but the same heuristic limits apply. Shown values are not a promise that the data is safe to share publicly. Do not share the private session URL.

Backend execution modes and unknown initialization metadata are reported conservatively. Only Terraform 1.5.5 with the local backend and the built-in `terraform_data` resource has been run for real, on macOS. No cloud provider, remote backend, OpenTofu release or other operating-system runtime has been certified. See [M01 evidence](docs/M01-verification.md) and [M02 evidence](docs/M02-verification.md).

## Reporting

Do not attach real state, plans, credentials, private session URLs, or unredacted CLI logs to a report. Supply the affected version, a description, and a minimal synthetic reproduction. A private reporting address has not been established; contact the repository owner privately before disclosing exploit details. No security-support SLA is offered for this alpha.
